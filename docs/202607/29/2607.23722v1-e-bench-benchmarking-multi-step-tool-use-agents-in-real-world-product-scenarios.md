## 摘要
大型语言模型（LLM）越来越多地被部署为智能体，在多步交互中与有状态环境进行交互：收集隐藏信息、组合工具调用并提交状态变更。我们将这种能力称为多步工具使用。现有基准测试推动了工具使用智能体的评估，但通常侧重于孤立的API调用、短轨迹或难以扩展或控制的设置。我们引入了E-Bench，这是一个全合成基准测试，包含三个产品领域的323个状态变更任务：王者荣耀、QQ音乐和腾讯会议。E-Bench将环境合成与任务解耦：图引导的数据库填充构建了可重用、无孤立的产品环境，而生成器-求解器不对称则创建了同时存在信息鸿沟和工具鸿沟的任务，要求智能体在改变状态之前发现隐藏数据并组合多个工具调用。结果通过数据库状态差异进行确定性评分。由于环境和任务都是合成的，E-Bench在环境层面可控，在任务层面可扩展。对11个前沿LLM的基准测试表明，多步工具使用仍然具有挑战性：最强模型的Pass^3仍低于60%，即使在E-Bench-Code扩展中使用代码执行，可靠性（Pass^3）仍低于70%。

## Abstract
Large Language Models (LLMs) are increasingly deployed as agents that interact with stateful environments over multiple steps: gathering hidden information, composing tool calls, and committing state changes. We refer to this capability as multi-step tool use. Existing benchmarks have advanced tool-use agent evaluation, but often focus on isolated API calls, short trajectories, or settings that are difficult to scale or control. We introduce E-Bench, a fully synthetic benchmark with 323 state-changing tasks across three product domains: Honor of Kings, QQ Music, and Tencent Meeting. E-Bench decouples environment synthesis from task synthesis: graph-guided database filling builds reusable, orphan-free product environments, while generator-solver asymmetry creates tasks with both an information gap and a tool gap, requiring agents to discover hidden data and compose multiple tool calls before changing state. Outcomes are graded deterministically by database-state diffs. Since both environments and tasks are synthetic, E-Bench is controllable at the environment level and scalable at the task level. Benchmarking 11 cutting-edge LLMs shows that multi-step tool use remains challenging: Pass^3 stays below 60% for the strongest models, and even with code execution in the E-Bench-Code extension, reliability (Pass^3) remains below 70%.

## 1. 核心问题与整体含义（研究动机和背景）

- **问题背景**：大语言模型（LLM）正被广泛部署为智能体，需要与有状态环境进行**多步交互**——收集隐藏信息、组合工具调用、提交状态变更。这种能力称为**多步工具使用**（multi-step tool use）。
- **现有基准不足**：当前基准（如 Gorilla、ToolLLM、BFCL）多聚焦于单步 API 调用或短轨迹，缺乏对部分可观测性、长程依赖、状态变更操作的评估。基于真实系统的基准（如 SWE-bench、WebArena）虽提供丰富交互，但难以扩展、成本高、易受数据隐私和服务演进影响，且存在数据污染风险。
- **本文目标**：构建一个**全合成、可控、可扩展**的基准 E-Bench，用于系统评估 LLM 在多步工具使用场景中的能力，要求智能体必须通过多步、并行的工具交互来发现隐藏数据并执行状态变更。

## 2. 方法论

- **核心思想**：将环境合成与任务合成**解耦**（decoupled），先构建可重用的产品级环境，再基于该环境合成状态变更任务，并通过**生成器-求解器不对称**（generator-solver asymmetry）强制引入信息差和工具差。
- **关键技术细节**：
  - **图引导数据库填充（Graph-guided database filling）**：依据表依赖关系（外键）构建拓扑序，依次填充表，确保引用完整性；使用强 LLM 作为约束合成器，通过插入工具写入记录，避免孤立记录。
  - **受约束上下文感知合成（Constrained Context-Aware Synthesis）**：填充时，LLM 接收表模式、已有记录、全局上下文，并通过只读查询选择候选实体，保证跨表一致性。
  - **验证与修复**：合成后运行确定性脚本修正语义错误（如时间顺序、聚合计数等）。
  - **领域工具构建**：基于数据库构建 CRUD 风格的 MCP 工具，暴露产品级语义（如搜索歌曲、创建会议）。
  - **任务生成**：生成器（Claude Opus 4.7）通过 `inspecting data → decide targets → modify state → summarize intent` 循环，记录数据库状态 diff 作为真实值；后续由三个强验证器（GPT-5.5、Opus 4.7、GLM-5.1）验证状态变更的正确性，过滤弱基线可解的任务。
  - **信息差**：生成器可访问全数据库和 SQL，但求解器只能通过领域工具观察环境，无法直接从提示中获得隐式目标。
  - **工具差**：生成器可使用代码执行（`exec_code`），基础求解器只能调用领域 MCP 工具；E-Bench-Code 扩展赋予求解器代码执行能力，部分闭合工具差。
  - **评估**：通过比较最终数据库状态与真实 diff 进行确定性评分（无 LLM 评判者），不支持部分得分。

## 3. 实验设计

- **数据集/场景**：三个合成产品领域——王者荣耀（110 任务）、QQ音乐（104 任务）、腾讯会议（109 任务），共 323 个状态变更任务。每个领域包含完整数据库（12-16 张表，76K 行数据）。
- **Benchmark 设置**：
  - **E-Bench（基础）**：求解器只能使用领域 MCP 工具。
  - **E-Bench-Code**：额外提供 `exec_code` 工具，允许 Python 代码调用领域函数。
- **对比方法**：11 个前沿 LLM：Kimi-K3、GPT-5.5、Opus-4.8、Grok-4.5、GLM-5.2、Qwen-3.7-Max、Hy3、Seed-2.1-Pro、Gemini-3.5-Flash、MiniMax-M3、DeepSeek-V4-Pro（附录还测试了 Muse-Spark-1.1）。

- **效率指标**：工具调用次数、回合数、输入/输出 token 数、API 成本。

## 6. 主要结论与发现

- **多步工具使用远未解决**：最强模型 Kimi-K3 在 E-Bench 上 Avg@3 仅 73.79%，Pass 3 仅 58.82%。所有模型平均 Avg@3 仅 54.56%。
- **可靠性是核心瓶颈**：Pass@3 与 Pass 3 之间存在巨大差距（如 Kimi-K3 从 87.62% 降至 58.82%），表明模型经常间歇性失败。
- **代码执行普遍提升性能但可靠性仍有限**：E-Bench-Code 下 Opus-4.8 取得最高 Avg@3（81.11%），但 Pass 3 仍低于 70%。弱模型（如 DeepSeek-V4-Pro）相对提升显著但仍低。
- **代码执行重塑排行榜**：强代码用户（如 Opus-4.8、Gemini-3.5-Flash）排名上升，且代码执行大幅降低工具调用次数和成本（MCP 调用平均减少 73.8%）。
- **能力差异**：代码执行在计算密集型任务（多条件过滤、全数据采集、聚合计算）上增益最大，对推理密集型任务（跨步依赖、精确边界判断）增益较小。
- **领域难度不均**：王者荣耀最难（Avg@3 约 43.6%），QQ音乐最易（约 61.4%）。
- **并行调用能力影响 token 效率**：强并行模型（如 GLM-5.2）消耗更少 token，弱并行模型（如 Grok-4.5、Seed-2.1-Pro）消耗更多。

## 7. 优点

- **全合成、可控、可扩展**：环境和任务均为合成，避免数据污染和安全问题；环境层面可控制数据分布，任务层面可批量生成。
- **确定性评估**：使用数据库状态 diff 而非 LLM 评判，结果稳定可复现。
- **解耦设计**：环境与任务分离，避免任务专用快照的局限性；共享环境鼓励智能体探索更广上下文。
- **信息差与工具差设计**：合理模拟真实场景，迫使智能体主动收集信息并组合工具。
- **细粒度能力分类**：六种能力类型的分析有助于理解 LLM 在不同子能力上的表现。
- **成本-效率分析**：提供了 API 成本与性能的 Pareto 前沿，对实际部署有参考价值。
- **代码执行扩展**：E-Bench-Code 隔离了工具差的影响，使计算与推理的贡献可分离。

## 8. 不足与局限

- **不开放代码与环境**：为防止 benchmark-specific 过拟合，未开源环境和任务数据，这限制了第三方复现和扩展（论文明确声明）。
- **领域覆盖有限**：仅三个产品领域（游戏、音乐、会议），可能不反映其他类型工具使用场景（如操作系统、数据库管理）。
- **未测试数据污染风险**：虽然声称通过合成数据缓解，但未实验性验证模型是否在类似合成数据上预训练过（如 GitHub 代码）。
- **缺乏对内部推理的分析**：所有评估基于行为结果，未深入分析模型思考过程（如思考链中的错误类型）。
- **仅考虑了单一解路径**：虽然评估最终状态而非轨迹，但任务生成可能隐含特定调用顺序，生成器错误可能影响任务质量（尽管有三验证器过滤）。
- **未涉及安全与对齐问题**：未测试模型是否会执行危险操作（如删除所有数据），也未评估对抗性输入。
- **缺少标准方差统计**：每任务仅三试，未提供置信区间或多次完整运行的统计。
- **API 成本依赖定价**：论文中成本计算基于特定时间点的 API 价格，可能不具长期稳定性。
