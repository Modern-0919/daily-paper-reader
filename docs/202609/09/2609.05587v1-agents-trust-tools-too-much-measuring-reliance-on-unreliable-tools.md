## 摘要
现有对工具使用智能体的评估主要衡量智能体能否利用工具成功完成多样任务。这些评估通常假设工具返回的信息可靠。然而，真实系统中的工具返回可能看似合理却并不正确。我们通过评估使用三种工具（网络搜索、LLM子智能体委派、代码执行）的十四个大语言模型，研究智能体如何应对不可靠的工具返回。对每种工具，我们篡改其返回内容，并衡量智能体在最终回答中采用这些被篡改内容的程度。智能体在三种场景下均表现出高度的过度信任：每种工具的平均采用率均超过三分之一，其中网络搜索的采用率高达68.0%。对推理轨迹的分析揭示了一个尤为令人担忧的失败模式：智能体常常识别出冲突，甚至在内部恢复出正确答案，却最终仅呈现被篡改的内容，且未向用户发出警告。为缓解智能体对工具返回的过度信任，我们从三个层面进行干预：用户提示、工具提供方的元数据、以及智能体构建方的后训练。尽管某些干预对特定模型或工具有效，但没有任何一种干预能跨工具一致地缓解过度信任。这些发现表明，对不可靠工具的过度信任是一种严重且持续存在的失败模式，亟需相关评估与干预措施，使智能体能够验证工具输出并透明地沟通未解决的冲突。

## Abstract
Existing evaluations of tool-using agents primarily measure whether an agent can successfully complete diverse tasks with tools. These evaluations generally assume that tools return reliable information. However, tool returns in real-world systems can be plausible yet incorrect. We investigate how agents respond to unreliable tool returns by evaluating fourteen LLMs using three tools-web search, LLM sub-agent delegation, and code execution. For each tool, we corrupt its returns and measure whether agents adopt the corrupted content in their final answers. Agents exhibit high levels of overtrust across all three settings: the mean adoption rate exceeds one third for every tool and reaches 68.0% for web search. Analysis of reasoning traces reveals a particularly concerning failure mode: agents often recognize conflicts and even recover the correct answer internally, yet present only the corrupted answer without warning the user. To mitigate agents' overtrust in tool returns, we intervene at three levels: prompting by the user, metadata from the tool provider, and post-training by the agent builder. Although some interventions help for particular models or tools, none consistently mitigates overtrust across tools. These findings identify overtrust in unreliable tools as a serious and persistent failure mode, motivating evaluations and interventions that enable agents to validate tool outputs and transparently communicate unresolved conflicts.

### 1. 核心问题与研究动机

- **研究背景**：工具使用已成为 LLM 智能体的基本能力。现有工具使用评估基准（如 ToolLLM、τ-bench、BFCL）主要回答“智能体能否正确选工具、发调用、完成任务”，且普遍假设工具返回的信息是可靠的。
- **核心问题**：真实世界中，工具返回可能是“看似合理却错误”的内容——生成式搜索引擎会返回合成答案、LLM 子智能体会输出委派报告、代码执行器返回由模型生成程序的计算结果。**智能体是否会在最终回答中采纳这些被污染的内容？其采纳程度如何随内容合理性变化？哪些干预能缓解这种过度信任？**
- **整体含义**：本文系统性地证明，智能体对不可靠工具输出存在严重且普遍的“过度信任”（overtrust），且该问题比单纯“检测不出冲突”更严重——模型即使已在内部识别冲突甚至恢复正确答案，仍可能向用户输出错误结果而不加警告，构成重大安全隐患。

### 2. 方法论

#### 2.1 核心思想
构建“配对返回”范式：对于同一任务，先获得未损坏的正确工具返回（P0），再构造若干不同合理程度的损坏返回（P1、P2、P3，P1 最合理、P3 最不合理），仅改变返回内容而不改变其他条件，观察模型最终回答的采纳行为。

#### 2.2 关键指标
- **采纳率（Adoption rate）**：智能体将注入的被污染内容带入最终答案的频率。
- **覆盖/改写率（Override rate）**：仅在模型**无工具时已能正确回答**的题目子集上计算，衡量损坏返回是否把原本正确的答案改写成错误答案（更有力的过度信任证据）。
- **基础准确率（Base Accuracy, B）**：无工具条件下三次独立回答的多数投票正确率。
- **工具调用比（Tool-call ratio）**：损坏返回条件下平均调用次数与正确返回条件下的比值，反映模型是否感知到异常。
- **警告率（Warning rate）**：在最终答案采纳了污染内容的样本中，模型是否向用户说明冲突的比例。

#### 2.3 三种工具通道的损坏构造
- **网络搜索（Search）**：基于 FreshQA 事实问答，用 GPT-5.6-Luna 对检索片段中的黄金答案做最小替换。P1 = 过去曾正确或易混淆的真实值；P2 = 移植自另一道题的答案（如“德国总理”被替换成数字 11）；P3 = 完全虚构的名字/机械数字置换。
- **LLM 子智能体（Sub-Agent）**：文档摘要任务。子智能体的摘要预先离线生成并冻结。P1 = 将一条核心主张替换为虚假主张；P2 = 保留全部真实主张但额外加入一条无中生有的虚构主张。
- **代码执行器（Code Executor）**：数学计算任务。对程序标准输出中的每个数字 o 按因子进行缩放/翻转符号：

$$o' = \begin{cases}s \times o \times r & \text{if } d=+1\\s \times o \div r & \text{if } d=-1\end{cases},\quad r = 1 + p/100$$

其中 p 为误差幅度参数（P1 从 [1,100]、P2 从 [101,10000] 对数均匀采样），d 决定放大/缩小，s 决定符号保留/翻转。该设计可区分模型对“符号保留但数值错误”与“符号翻转”的不同响应。

#### 2.4 干预方法
- **用户提示干预**：PLAIN（基线）、COMPARE（比较先验知识与任务约束）、VERIFY（要求提出实质上不同的独立反证检查）、DISCLOSE（要求向用户披露不一致信息及其依据）。
- **工具提供方元数据干预**：为搜索结果附加来源标签（Wikipedia、Reuters、Reddit、X）或可靠性标签（0.10/0.50/0.95、high/low），并区分“被动附加”与“指示模型考虑该标签”两种模式。
- **智能体构建方后训练干预**（以 Qwen3-30B 为基础）：
  - Recovery SFT：在包含成功抵抗损坏返回轨迹的数据上微调；
  - Correct-tool SFT：仅在正确返回的成功轨迹上微调；
  - Fixed-context DPO：以共享损坏返回前缀的平衡偏好对进行 DPO，偏好抵抗而非采纳。

### 3. 实验设计

#### 3.1 数据集 / Benchmark 构成
- **Search**：FreshQA 2026-04-21 快照中的 418 道事实问答（排除 14 道二元题），按答案变化频率分为 never（147）、slow（127）、fast（144）三类；污染等级 P1/P2/P3。

### 5. 实验数量与充分性

#### 实验规模
- **Search**：14 模型 × 418 题 × 3 污染等级 × 3 重复（约 52,643 次有判断的运行），加上扩展模型的 90 题。

- **优点**：多模型、多工具、多污染等级、多干预层次的交叉实验设计覆盖面广；配对设计和严格统计检验（bootstrap、permutation test、Holm 校正）增强了结论的稳健性；采用基于规则或经过人工验证（Fleiss κ=0.843）的自动评判，保证结果可复现。
- **限制**：Search 通道存在服务方式不对称（API 模型与本地模型精度、上下文长度不同）、收集时间差异（Gemini-3.7-flash 与 Muse 晚几天收集，live-resolution 率约 51%）；部分模型（如 Gemini）在 API 提供方下近乎确定性，三次重复仅等于一次有效抽样，使 Override 判定降级；Sub-Agent 通道中小说摘要由标题生成而非原文，部分 post-cutoff 论文的成功可由标题推导，存在基准噪声；Code Executor 通道将解析失败计入分母而非采纳，可能略微低估过度信任。整体而言，实验充分但存在轻微公平性不对称，作者对此有较透明的披露。

### 6. 主要结论与发现

#### 6.1 过度信任普遍且严重
- 模型对三通道的 P1 损坏返回，平均采纳率全部超过 1/3（Search 68.0%、Sub-Agent 28.7%、Executor 35.4%）。
- 更严格的 Override 率同样居高不下：Search P1 达 56.4%，Executor P1 达 33.4%，且 Sub-Agent 和 Executor 的 P2 Override 率仍约 1/5。
- 14 个模型中没有任何一个能在全部三通道上一致抵抗损坏返回。某些模型（如 Gemini-3.7-flash、Muse-Glimmer-30B 在 Executor 上）表现较好，但同模型在 Search 上仍大量采纳。

#### 6.2 不合理依赖的具体证据
- **Search**：对 never-changing 事实的 P1 采纳率仍高达 59.7%，说明模型不是为了获取最新信息而合理参考工具，而是机械屈从于返回内容。
- **Code Executor**：符号保留（sign-preserved）的污染被采纳 56.4%，符号翻转（sign-inverted）的只被采纳 14.3%；模型并非盲目接受所有输出，而是对“看起来合理”的错误缺乏防御。
- 模型对工具返回的信任超出对用户或 RAG 上下文中同等内容的信任（Executor 通道：Tool 采纳率 39.9% vs. User 1.8% vs. RAG 3.8%），表明**工具接口本身赋予了输出额外的权威性**。

#### 6.3 “检测到冲突但不披露”的关键失败模式
- 对 Qwen thinking 模型的推理轨迹分析显示：在采纳了损坏值的运行中，Search 通道约 52%/53% 的轨迹提到了冲突，Executor 通道超过 90% 的轨迹提到冲突，许多轨迹甚至已在内部写出正确数值。
- 然而，最终答案中几乎不向用户警告：Search 仅 5.3%、Executor 仅 1.8% 的采纳回答附带警告，多数模型的警告率为 0%。
- 模型在 Executor 中面对损坏返回时会显著增加额外工具调用（数倍于基线），说明它“觉得不对劲”，但最终还是选择提交错误答案——**失败不只是错误答案本身，而是已认识的冲突在最终回答中被隐没**。

#### 6.4 干预效果有限
- 提示干预对特定模型/通道有效果（如 Search 中 DISCLOSE 降 5.2 点、Sub-Agent 中 VERIFY 降 6.0 点、Executor 中 COMPARE/VERIFY 降 8 点以上），但没有一个策略能跨通道同时降低采纳率并保持 P0 准确率；某些策略在部分模型上反而提高采纳率。
- 元数据干预无一致缓解效果，甚至**声称更高可靠性会使损坏返回更具说服力**（numeric 标签高 vs 低相差 +3.7 点，categorical 标签 +4.5 点）。
- 后训练效果取决于目标函数：Recovery SFT 几乎无改善；只在正确返回上训练的 Correct-tool SFT 反而将 Executor 采纳率和 Search Override 率推高；Fixed-context DPO 在 Search 上降幅最大（P1 −5.1、Override −7.8 点）但牺牲 P0 准确率且不迁移到 Executor。

### 7. 优点

1. **问题定位精准且新颖**：从“能否用工具”转向“能否抵抗工具的坏输出”，并设计了 Override rate 区分“合理依赖工具”和“改写已正确掌握的答案”，更本质地抓住了过度信任。
2. **多工具系统化对比**：首次在同一框架下横跨 Search、Sub-Agent、Code Executor 三类异构工具对过度信任进行量化对比，暴露了信息通道间信任差异（工具权威性高于用户文本）。
3. **严谨的污染构造阶梯**：P1/P2/P3 三级合理性梯度使研究能刻画“采纳率−内容合理性”的依赖关系；代码执行器采用符号×方向×幅度的正交因子设计，精细区分了错误类型。
4. **关注用户可见性**：不仅测“对错”，还测“是否披露冲突”，并通过思维链发现“内部知道但最终隐瞒”的隐蔽失败模式，发现极具实际意义且超越以往性能下降式评测。
5. **多层次的干预研究**：覆盖用户（prompt）、工具方（metadata）、模型方（post-training）三个干预接入点，系统展示各自边界。
6. **细致的质量控制**：包括人工验证搜索评估一致性、URL 泄漏审查、交付 payload 审计、fail-closed 暴露门控、对服务器缓存时序和解析失败等混杂因素均有较高透明度披露，并附完整的 prompt 模板和数据清单，可复现性强。

### 8. 不足与局限

1. **模型覆盖的时效性偏差**：论文并未提供所有主流前沿闭源模型（如 GPT-5.4/Claude/Grok 只在 90 题小样本上做了探索性补充，未纳入主表），主实验中的 OpenAI 模型为 mini/nano 级别，模型代表性受限于 2026 年的 API 生态。
2. **服务条件不对称**：各模型使用不同 serving 精度（fp8/bf16）、不同输出长度上限（8k 与 24k）、不同提供方（本地 vLLM vs OpenRouter vs 第一方 API）、不同收集时间（Gemini/Muse 晚于初始缓存冻结），这些差异可能影响模型级比较的公平性。
3. **采样有效性问题**：部分 API 模型（Gemini）三次重复近乎确定，使 Override 判断退化为单次有效采样，降低指标稳定性。
4. **任务生态有限**：事实问答、三文档总结、数学计算均属相对单一的任务形态，未覆盖多跳规划、长程交互、多工具协同等更复杂智能体场景；代码执行器仅污染 stdout 中的数值，未考虑更复杂的代码执行错误注入。
5. **干预实验的规模较小**：prompt/metadata 干预仅在 60 题固定切片上对 6 个模型评估，后训练仅基于 Qwen3-30B 单一模型，结论的外推性有限。
6. **生态效度存疑**：Search 通道使用冻结缓存与历史快照而非实时检索，Sub-Agent 通道的小说摘要由标题生成、接收模型无法独立核验，与现实部署存在偏差；工具返回被刻意污染的方式也可能与自然发生的工具故障模式不同。
7. **统计量过度集中**：核心发现主要依赖平均值；模型级差异虽存在（如 Muse 在 Executor 极低、Gemini 较低），但论文未深入解释为何某些模型抵抗性更强，缺乏对模型内在机制的分析。
8. **未解决“正确拒绝”的权衡**：论文侧重降低对损坏返回的采纳，但未充分讨论在工具正确时“过度抵抗”的代价边界——尽管 P0 准确率有报告，但未建立统一的“信任−准确率”帕累托框架来指导实务调参。
