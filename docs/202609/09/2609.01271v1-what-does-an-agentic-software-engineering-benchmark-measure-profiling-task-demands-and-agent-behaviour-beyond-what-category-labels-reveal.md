## 摘要
代理软件工程基准测试通常通过名义类别标签（如“缺陷修复”或“功能实现”）进行概括，然而，具有相同标签的基准测试却是通过截然不同的策展流程构建的。因此，标签很少揭示基准测试所要求的工程工作。我们引入了Spread--Novelty--Centrality（SNC）概况，这是一种基于实证软件工程研究的三轴特征描述，用于刻画仓库级编码任务的需求。我们将该概况应用于五个广泛使用的基准测试，以及两个模型家族在三个规模下的14,922条轨迹，并报告了三个发现。(1) 标签是任务需求的不可靠代理，因为每对基准测试在至少两个SNC轴上存在统计上的显著差异，且这些差异可追溯到具体的策展决策。(2) 代理行为揭示了人类编写的黄金解决方案无法揭示的需求。在问题陈述未提供提示的情况下，代理会产生比黄金解决方案更大的解决方案，而在策展过程膨胀了黄金解决方案的情况下，代理会产生更小的解决方案。任务的表述方式会影响代理的产出。(3) 任务需求与成功率普遍相关，对于每个家族和规模，成功运行的轨迹集中在低SNC区域，而成功的特征行为则具有家族特异性。Claude通过匹配黄金解决方案的范围来取得成功，其在文件上的均等份额从小规模时的$0.17$上升至最大规模时的$0.54$。Qwen则在各个规模上都通过超越黄金解决方案的范围来取得成功，而对于两个家族来说，编辑过少都标志着失败。

## Abstract
Agentic software engineering benchmarks are typically summarized by nominal category labels such as "bug fix" or "feature implementation," yet benchmarks carrying the same label are built through very different curation pipelines. A label thus reveals little about the engineering work a benchmark demands. We introduce the Spread--Novelty--Centrality (SNC) profile, a three-axis characterization of the demands of repository-level coding tasks, grounded in empirical software engineering research. We apply the profile to five widely used benchmarks and 14,922 trajectories of two model families at three scales, and report three findings. (1) A label is an unreliable proxy for task demands, as every pair of benchmarks is statistically separated on at least two SNC axes, and the separations trace back to specific curation decisions. (2) Agent behaviour reveals demands that the human-written gold solution cannot. Agents produce larger solutions than the gold where problem statements withhold hints and smaller ones where curation inflates the gold. How a task is phrased shapes what an agent produces. (3) Task demands correlate with success uniformly, with resolved runs concentrating in the low-SNC region for every family and scale, whereas the behavioural signatures of success are family-specific. Claude succeeds by matching the scope of the gold solution, and its parity share on files rises from $0.17$ at the smallest scale to $0.54$ at the largest. Qwen succeeds by exceeding the gold scope at every scale, and editing too little marks failure for both families.

## 1. 论文的核心问题与整体含义（研究动机和背景）

随着大型语言模型（LLM）能力从函数级代码补全拓展到仓库级、代理式（agentic）软件工程任务，评估这些任务的基准测试也日益丰富。然而，该领域描述任务的方式却严重滞后——基准论文通常仅以"缺陷修复"（bug fix）或"功能实现"（feature implementation）之类的**名义类别标签（nominal category label）**来概括任务集合，社区据此把模型分数解读为某一类别的能力。但近期的证据（如 Shibaev et al., 2026）表明，在一个基准上微调获得的提升难以迁移到看似相似的任务上。

本文的核心论点在于：**标签掩盖了任务间的真实差异。** 即使共享同一基准标签，由于任务构建管道（PR筛选、问题陈述的撰写、测试约束、提示信息多寡等）存在显著差异，两个基准可能要求的是截然不同的工程工作。因此，本文提出一个问题：**一个代理软件工程基准测试到底衡量了什么？** 论文主张需要一种比标签更细粒度、更基于实证SE研究原理的任务表征方法，以推动回答三个环环相扣的问题——任务需要什么工程工作、代理如何行为、哪些因素决定成功解决。

整体含义：是为基准测试提供"构念效度"的工具，让模型训练者、工具构建者、基准作者和软件工程师能在任务需求层面（而非标签层面）对基准与智能体进行量化分析和比较。

## 2. 论文提出的方法论

### 2.1 核心思想
针对单一黄金补丁（gold patch）过于单薄、名义标签过于粗疏的问题，本文提出 **SNC画像（Spread–Novelty–Centrality Profile）**，以三个轴向刻画仓库级编码任务的工程需求：

- **Spread（分散度）**：变更在代码库中的分布范围。
- **Novelty（新颖性）**：添加新代码与删除/改写既有代码的权衡程度。
- **Centrality（中心性）**：所修改代码在架构与演化中的重要程度。

### 2.2 技术指标细节

**Spread 由两个互补指标构成：**
- **归一化熵（Normalized entropy, \(H_n(P)\)）**：对变更在各文件间的分布进行香农熵计算并做 \( \log_2 n \) 归一化。熵高说明变更均匀分布在多个文件、没有单一主导文件——需求更高。
- **半径（Radius, \(R(P_i)\)）**：度量被修改文件的路径在仓库目录树中的'跨度'，以被触碰文件的祖先目录集合大小除以仓库全部目录节点数，反映变更文件在结构上的"距离"。

**Novelty（单一指标）**：
\[
\text{Novelty}(P)=\frac{|\text{add}(P)|}{|\text{add}(P)|+|\text{del}(P)|}
\]
纯新增=1、纯删除=0、重写≈0.5。

**Centrality 由四个指标构成：**
- **Fan-in / Fan-out**：基于模块（module）的导入依赖图。Fan-in 高说明改的是被广泛依赖的核心抽象；Fan-out 高意味着改的是需要了解大量外部依赖的协调点。均以仓库全局总进口/出口数归一化。
- **Churn（变更热度）**：在黄金补丁基线的最近 180 天提交历史窗口内，随机一次提交曾触碰该补丁涉及文件的概率——高 churn 意味着修改的是仍在积极演化、需求未定的"热路径"代码。
- **Mass（质量/复杂度）**：被修改的 callable 的规模（源码行数×圈复杂度）在仓库总 mass 中的占比。

### 2.3 聚合与统计方法

- 每个轴集约化为标量：Novelty直接取值；Centrality对四个重尾指标取 log₁₀ 后求未加权均值；Spread仅用半径（熵在占主导的单文件补丁上被迫为 0，聚合会失真），并对半径取 log 变换。
- 所有轴向标量经 z-score、min-max 映射到 [0,1]。
- 使用 **Scott-Knott Effect Size Difference (ESD)** 检验，按统计显著（α=0.05）和效应量（|d|≥0.2）比较基准间差异。
- 在 RQ3 中使用**卡方独立性检验**（BH-FDR校正p值）并辅以 **Cramér's V** 效应量评估不同结局（解决/未解决）的条件行为是否显著分离。

## 6. 主要结论与发现

### 6.1 RQ1——标签是任务需求的不可靠代理
- 五个基准在三个 SNC 轴向上均被 ESD 划分出四个不同聚类，且**每一对基准至少在两个轴向上统计分离**。
- 三个 feature 基准彼此分开，验证了表面标签相同的任务需求实则差异巨大。
- 分离均可**追溯到具体的策展决策**：
  - FeatBench 的仅修改、不得增删函数的筛选 → Novelty 被压缩至中低区间（近似 in-place 重写）；
  - FeatureBench 的测试先行 carve-out（留桩）→ Novelty 接近饱和 1.0；
  - FEA-Bench 只选新增新组件的 PR → 新代码无入边依赖、无历史 churn，Centrality 显著低。

### 6.2 RQ2——代理行为揭露标签与黄金补丁都看不见的隐性需求
- **补丁冗长度（verbosity）与基准文字提示高度相关**：
  - 无提示的 FeatBench → 代理相对黄金严重过度产出（files/lines/callables 全面放大）；
  - 提示型 FEA-Bench → 几乎停在 parity（可预期，但反向印证"措辞规定了产出形状"）；
  - FeatureBench → 代理产出明显小于黄金补丁，且其特征有 33.8% 黄金行是注释/文档字符串——策展"注水"了黄金补丁；
  - SWE-bench/SWE-Gym → 补丁简单紧凑，代理近似 parity。
- **探索宽度（exploration breadth）在所有基准间无统计差异**——"广读之后窄改"是代理的固有行为而非任务响应，其中排序方向虽具启发（FEA-Bench 提示抑制探索、FeatureBench 空桩迫使广探索）但未达显著。

### 6.3 RQ3——任务需求与成功普遍关联，行为签名因家族而异
- **普适规律：几乎所有 SNC 指标中，解决运行的分布都集中在低 bin**，未解决运行向高 bin 偏移（两家族、三规模一致）。Novelty 例外——解决集中在两个极端，而在中间"重写"区间未解决占比较大。
- **家族特异性的成功行为**：
  - **Claude 通过 parity 成功**：parity 份额随规模从 S=0.17 → M=0.41 → L=0.54（files）；探索也更聚焦（parity 0.09→0.34），小号 Claude 过度产出、大号收敛到黄金范围。
  - **Qwen 通过超过 2× 的成功**：在各规模的 files/lines/callables 上 resolved 峰值始终在 >2× 带（约 0.6–0.7），parity 仅 0.2 左右。
  - **欠编辑（sub-parity）对两家族都标志失败**。
- 统计验证：22/24 footprint 格子及全部 42/42 SNC 格子结局分离显著（BH 校正 p<0.05），Cramér's V 中位数 0.20，最大 0.40。

### 6.4 启示
按受众给出建议：模型训练者应分区（SNC）报告成绩、在数据收集中补足未覆盖区（尤其高 Spread+高 Centrality）；工具/框架构建者应把 scope 指导设为可配置的逐模型选项，并加入"欠产出"运行时检测；基准作者应在发布时附带逐实例 SNC 画像并声明策展排除的 SNC 区域；工程师可据此将低 SNC 任务委派给小模型、为高 SNC 任务保留强模型和复核。

## 7. 优点

1. **方法创新性与理论根基好**：SNC 画像的三个轴向均从经典实证 SE（Hassan 2009 变更熵、McCabe 复杂度、fan-in/out、churn 文献）得到支撑，将 LLM 基准的分析引入原理化的软件工程度量体系，而非简单的规模/成本统计。
2. **"画像×策展管道"的双向互证关系是本研究的亮点**：不仅证明基准间差异显著，更将这些差异清楚地追溯回具体的构造决策（testability filter、carve-out、PR筛选），形成了可操作的因果叙事。
3. **行为视角的引入很关键**：将 RQ2 的焦点限制在代理成功解决的任务上，使代理补丁与人类黄金补丁的比较具有"两种正确解比较"的干净语义，从而成功分离了"能否解决"与"解的形状"，揭示出问题陈述措辞单独产生影响。
4. **统计严谨**：采用 Scott-Knott ESD、BH-FDR 校正卡方、Cramér's V 效应量等多层检验，规避多重比较与"大样本显著"陷阱。
5. **研究范围广而清晰**：覆盖 issue resolution + feature implementation 两大类型的五个主流基准、代表上限的前沿模型、多个规模尺度；轨迹量达 1.5 万，分析和可视化丰富（雷达图、分箱分布图、band 图）。
6. **有对社区直接的产出价值**：公开代码仓、转换后的 FEA-Bench/Harbor 任务格式、逐实例 SNC 画像的发布建议等，提升了可复现性和后续使用性。

## 8. 不足与局限

1. **基准覆盖有限（语言单一）**：五个基准全部为 Python-only，SNC 多个指标（mass、fan-in/out、callable 分析）依赖语言感知工具，推广到 Java、TS 等多语言需重搭解析链。另只覆盖两类任务（issue resolution 与 feature implementation），未纳入重构类（如 RefactorBench）等可能占据不同 SNC 区域的任务类型。
2. **SWE-Gym 的适用性存疑**：SWE-Gym Lite 本为训练环境不是测试基准，将其纳入 SNC 分布对比虽可刻画任务，但作为评估 benchmark 可能带来对 Qwen 系列数据污染、分数高估的风险。
3. **模型/harness 混淆**：Claude 与 Qwen 两家族分别运行于 Claude Code 和 Qwen Code 两个不同 harness。家庭间行为差异（parity vs over-production）无法完全剥离 harness 影响，作者亦承认这一点，因此"模型族特异性"结论需谨慎理解。
4. **语义/架构度量的简化**：Mass 与 fan-in/out 都只覆盖 Python 静态粒度；近似于模块级别的 churn 窗口（180 天）虽常规却未必适用不同频率的仓库；熵在单文件补丁被强制取 0 的取舍虽然解释清楚，但排除了"单文件+多个分散逻辑"的细粒度复杂度。
5. **结果表达上缺少成功率绝对值**：文章没给每个基准每模型的解决率报表，读者无法把 SNC 分布与绝对成功率直接对照，依赖图表稍显不便。
6. **计算成本未透明化**：无任何 GPU/推理/时间记录，影响经济成本与复现难度的估计。
7. **有效性证明的边界**：RQ3 的"共性 vs 特异性"结论只基于一次快照式的基准与模型管线。模型快速迭代下"小 Claude 过度产出、大 Claude parity"这类 scale 效果是否会持续，仍需未来纵向验证。
