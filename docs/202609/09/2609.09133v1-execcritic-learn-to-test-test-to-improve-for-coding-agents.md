## 摘要
执行反馈可以引导编码智能体正确修复代码库，但前提是测试能捕获问题所要求的行为。智能体生成的测试可能编码不完整或不正确的行为目标；当同一轨迹同时编写补丁和测试时，它们的错误可能相互一致并产生虚假的自信。我们提出了ExecCritic，将“测试—验证—修订”脚手架与角色特定的强化学习配方相结合，用于在其中训练智能体。该脚手架将测试构建与源代码修复分离：一个测试智能体独立生成代码库原生测试，一个故障封闭式测试框架对这些测试进行验证并冻结，一个修复智能体则根据其执行反馈修改源代码，而不更改测试。两个角色均使用Qwen-3.5-35B-A3B作为骨干，并分别进行训练。在“学会测试”阶段，测试智能体学习生成行为上有效的测试，能够区分正确与错误的补丁。在“测试改进”阶段，修复智能体学习直接任务解决和反馈引导的修订。在SWE-bench Verified上，测试质量决定了反馈是否有帮助：在保持基础修复智能体不变的情况下，基础测试智能体生成的测试将解决率从无测试基线（61.2%）降至57.3%，而GPT-5.6-sol的测试将其提升至65.3%。角色特定的后训练将Qwen测试智能体的基础到金标准成功率从22.2%提升至62.2%；组合两个后训练的Qwen智能体达到72.6%，比原始无测试基线高出11.4个百分点，且在评估时无需更强模型或Oracle反馈。代码已公开于https://github.com/MSR-Orchard/execcritic。

## Abstract
Execution feedback can guide coding agents toward correct repository repairs, but only when the tests capture the behavior requested by the issue. Agent-generated tests can encode incomplete or incorrect behavioral targets; when the same trajectory writes both the patch and the test, their errors can agree and create false confidence. We introduce ExecCritic, combining a test--verify--revise scaffold with a role-specific reinforcement learning recipe for training agents within it. The scaffold separates test construction from source-code repair: a Test agent independently generates repository-native tests, a fail-closed harness qualifies and freezes them, and a Repair agent revises source code from their execution feedback without changing the tests. Both roles use Qwen-3.5-35B-A3B as the backbone and are trained separately. In Learn to Test, the Test agent learns to produce behaviorally valid tests that distinguish correct from incorrect patches. In Test to Improve, the Repair agent learns both direct task resolution and feedback-guided revision. On SWE-bench Verified, test quality determines whether feedback helps: holding the base Repair agent fixed, tests from the base Test agent reduce resolved rate from a no-test baseline of 61.2% to 57.3%, whereas tests from GPT-5.6-sol raise it to 65.3%. Role-specific post-training raises the Qwen Test agent's Base-to-Gold success from 22.2% to 62.2%; composing the two post-trained Qwen agents reaches 72.6%, an 11.4-point gain over the original no-test baseline without stronger-model or Oracle feedback at evaluation time. Code is publicly available at https://github.com/MSR-Orchard/execcritic.

## 1. 核心问题与研究动机

- 在代码库级（repository-level）缺陷修复任务中，智能体通常需要在一次轨迹中同时生成**修复补丁**和用于验证的**测试**。然而，当同一模型/同一轨迹既写补丁又写测试时，生成的测试可能编码不完整或错误的行为理解，并与补丁共享相同盲点，导致错误的补丁通过错误的测试并产生“虚假通过”的假象。
- 执行反馈对修复有效性的关键在于**测试是否真正捕获了问题要求的行为**。若不解决测试质量与验证独立性问题，执行反馈不仅无益，甚至会降低修复率（实验显示同一修复模型使用其自身生成的测试后，解决率从 61.2% 跌至 57.3%）。
- 论文由此提出两个需求：(1) 提升生成测试的行为质量；(2) 将测试定义与源补丁修订解耦，即让验证准则*独立于*修复轨迹，防止修复者“削弱测试来迎合补丁”。

## 2. 方法论：ExecCritic

### 2.1 核心思想：测试—验证—修订（Test–Verify–Revise）脚手架

ExecCritic 将角色分离为两个互补的策略：

- **测试智能体（Test agent）**：基于 issue 和 Base 仓库，独立生成一个“测试包（Test bundle）”，包含：
  - `test.patch`——代码库原生（repository-native）回归测试补丁；
  - `test_command`——精确的测试执行命令；
  - `test_contract.json`——结构化行为契约（入口、触发、预期行为、证据等）。
- **故障封闭式（fail-closed）验证器（Harness）**：验证测试包格式、在 Base 上必须干净失败（clean failure）、在 Gold（参考修复后仓库）上必须通过；然后将此测试*固定不变*地提供给修复阶段使用。
- **修复智能体（Repair agent）**：仅修改源代码补丁，反复接收固定测试的执行反馈（PASS/FAIL，有界输出），并迭代修订。测试来源对其隐藏（hidden verifier），防止其修改或依赖测试源码。

### 2.2 两阶段管线

| 阶段 | 目标 |
|---|---|
| **Learn to Test** | 训练测试智能体生成行为有效、可判别（能区分正确与错误候选补丁）的回归测试。 |
| **Test to Improve** | 训练修复智能体：既具备直接初始修复能力（Round-0），也能依据固定的测试执行反馈做有条件的源码修订。 |

### 2.3 关键公式与训练细节

- **Base-to-Gold 判别式**（测试有效性指标）  
  \(Q_x(b)=B_x(b) \cdot G_x(b)\)  
  其中 \(B_x(b)=1\) 表示在 Base（buggy）仓库上干净失败，\(G_x(b)=1\) 表示在 Gold 仓库上通过。
- **测试智能体奖励函数**：依据是否提交、Base/Gold 结果和候选集上的均衡准确率 \(BA\) 分级赋分（–0.2 到 1.0），并加入轨迹长度惩罚。
- **修复智能体奖励函数**：依据补丁是否可用、所选测试是否通过、完整官方评测是否正确、以及是 Round-0 直解还是修订后解决，赋予 0 到 1.5 不等的奖励；禁止修改测试，违反者得 0。
- **训练策略**：分别使用 SFT + GRPO（group relative policy optimization）。Test 阶段先用 DeepSeek-V4-Flash-0731 生成的 5,000 个教师轨迹做有监督微调，再用在线 GRPO（DAPO 动态采样）；Repair 训练使用固定 Oracle F2P 测试作为受控反馈源。

### 2.4 自动化评测与迭代机制

- 测试包提交后由 harness 在隔离 Base 上执行；必须实现干净失败才会被录用并交给修复阶段。若测试生成在 Base gate 失败，则该实例仍保留 Round-0 补丁送官方评测（不剔除分母）。
- 修复阶段每实例最多 5 轮修订，每轮最多 40 个 turns；收到 PASS 则立即强制提交；预算耗尽也强制提交当前补丁，全部交给官方隐藏测试（F2P + P2P）裁决。

## 6. 主要结论与发现

1. **测试质量决定反馈的“得与失”**：固定 Qwen 基础修复智能体，用基础 Qwen 生成的测试会使解决率从 61.2% 降至 57.3%；用 GPT-5.6-sol 生成的测试则升至 65.3%；Oracle F2P 反馈升至 69.4%。
2. **角色定制后训练有效**：
   - 测试智能体 Base-to-Gold 成功率 22.2% → SFT 39.6% → RL 62.2%（接近 Codex-5.3 的 61.0%，但低于 GPT-5.6 的 87.8%）；
   - 修复智能体无测试 Round-0 解决率从 61.2% 升至 68.3%。
3. **组合增益显著**：RL 版测试智能体 + 完整 T2I 修复智能体在 SWE-bench Verified 上达 **72.6%**，比原始无测试基线高 **11.4 个百分点**；比单用无反馈的 trained Repair 高 4.3 个百分点；比训练时用生成的测试（70.9%）更好，说明干净反馈（Oracle）有助训练。
4. **额外分析**：删去直接解决奖励会削弱 Round-0（66.4%）但最终率仅略降；带推理链可见的教师 SFT 能显著提升后续 RL 空间（RL 后 62.2% vs. 36.2%）；测试生成可迁移到 Rust/C++，但 Java/C 上表现差。

## 7. 方法/实验设计的优点

- **独特视角**：形式化解释了“补丁与验证证据同轨迹耦合”的问题（Equation 1），并针对性设计固定测试方案，有效解决了自洽盲点问题。
- **角色分离清晰**：训练目标与奖励函数分开定义，避免了协同退化或测试不可信风险。
- **故障封闭与保守通过机制**：Base clean failure 作为必要条件、Gold 离线审计用于训练奖励但不进入在线决策、操作错误不算行为失败，设计严谨。
- **真实性高度可控**：所有中间门结果与官方评测分开记录，官方结果不回灌到轨迹。
- **大规模真实基准与可复现细节**：提供了完整 hyperparameter 表、prompt 模板、runner 命令、门控协议（附录长达 35 页），并在 Orchard 框架中开源代码。

## 8. 不足与局限

- **分工训练而非共享权重**：作者自述当前无法训练同一模型完成两个角色，无法端到端优化整体回路；未来需研究共享权重与角色条件化训练的稳定方法。
- **可迁移性受限**：测试智能体的推广依赖代码库的运行环境与语言；Java（2.4%）/C（26.1%）上的低成功率提示跨语言适用性不佳。
- **覆盖度问题**：受限于单一行为目标的测试包难以满足需要多个 F2P 行为的任务（SWE-bench Pro 上增益仅 0.7 pp，而 Oracle 可加 11.8 pp）。
- **无显著性与计算量匹配缺失**：平均值之间的差异未做统计检验；组合系统的收益也可能部分来自额外测试生成与更多推理计算。
- **特定模型的不可复现性**：论文所提 GPT-5.6、Qwen-3.5、DeepSeek-V4-Flash 为虚构未来版本，不能用于实际验证；数值结论存在不确定性。
- **存在基础性维护风险**：Harness 维护、环境不一致与测试泄漏虽积极处理（如 evidence-gated evolution 协议），但自动化 harness 的可靠性没有直接测量，Gold 审计仅用于训练/离线分析。
- **修复智能体被测试“卡住”时有强制提交风险**：若测试正确但预算用尽，最后也会强提潜在错误补丁，可能对总体结果有负面偏差影响。
