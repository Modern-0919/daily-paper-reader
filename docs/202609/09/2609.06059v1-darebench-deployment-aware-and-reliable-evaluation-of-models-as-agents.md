## 摘要
随着大型语言模型从问答系统演变为通用智能体，评估必须超越静态答案正确性，以涵盖多模态感知、多步执行、工具使用和工件交付。然而，现有基准通常与特定任务类型、执行环境或评分协议绑定，限制了其在部署决策中的可比性、可解释性和可靠性。我们提出DAREBench（面向部署的可靠模型智能体评估），这是一个旨在捕捉工作负载变化并支持可靠智能体评估的基准。基于共享的OpenClaw执行环境，DAREBench将来自22个源基准的233个任务组织成由输入模态和执行形式定义的$2\times3$工作负载矩阵，并在统一的基于合约的协议下进行评估，辅以基于证据的分数审计。我们评估了23个商业API模型和12个本地部署的开源权重模型，覆盖7,587次模型-任务运行，报告了准确性和token消耗以及API模型的参考成本。结果表明，没有单一模型在所有工作负载组中占主导地位，文本和多模态任务表现出不同的准确性-成本权衡，本地开源权重模型在若干组中具有竞争力，但总体上仍落后于前沿商业模型。这些发现表明，智能体部署和模型选择应考虑工作负载概况、部署模式及准确性-成本权衡，而非依赖单一总分。

## Abstract
As large language models evolve from question-answering systems into general-purpose agents, evaluation must move beyond static answer correctness to assess multimodal perception, multi-step execution, tool use, and artifact delivery. However, existing benchmarks are often tied to specific task types, execution environments, or scoring protocols, limiting their comparability, interpretability, and reliability for deployment decisions. We introduce DAREBench (Deployment-Aware and Reliable Evaluation of Models as Agents), a benchmark designed to capture workload variation and support reliable agent evaluation. Built on a shared OpenClaw execution environment, DAREBench organizes 233 tasks selected and adapted from 22 source benchmarks into a $2\times3$ workload matrix defined by input modality and execution form, and evaluates them under a unified contract-based protocol with evidence-based score auditing. We evaluate 23 commercial API models and 12 locally deployed open-weight models over 7,587 model--task runs, reporting accuracy and token consumption alongside reference costs for API models. Results show that no single model dominates all workload groups, text and multimodal tasks exhibit distinct accuracy--cost trade-offs, and local open-weight models are competitive in several groups but still trail frontier commercial models overall. These findings suggest that agent deployment and model selection should consider workload profiles, deployment mode, and accuracy--cost trade-offs rather than rely on a single aggregate score.

### 1. 核心问题与整体含义（研究动机与背景）

- **研究背景**：大语言模型（LLM）正从独立问答系统演变为通用智能体系统的核心决策组件，需要具备感知、推理、规划、工具使用与工件交付等能力。相应地，模型评估应从静态输入-输出评测转向在工具、上下文、时间和成本约束下的端到端执行评测。
- **核心问题**：现有评估框架无法充分支持这一转变。主要体现在三个方面：
  - **可解释性不足**：智能体任务在输入模态、执行过程与工具依赖度上差异显著，单一总分掩盖了模型在不同工作负载上的强弱差异；
  - **因果归因困难**：任务依赖不同的智能体框架、工具接口和执行协议时，观测差异将模型能力与运行时兼容性混为一谈；
  - **分数可信度存疑**：开放式智能体任务涉及多步操作与工件交付，仅匹配最终文本无法验证任务是否真正完成。LLM裁判（judge）可能在工具未执行、任务超时或关键工件缺失时错误给出正分。
- **论文主张**：智能体评估必须通过“统一工作负载组织、统一执行环境控制、统一结果验证”三个途径来支撑部署决策，而不只是扩大基准规模。

### 2. 方法论：核心思想、关键技术细节

针对上述问题，作者提出DAREBench，由四个核心组件构成：

#### （1）任务构建与分类（Workload Construction）

- 从22个公开源基准中筛选233个任务，经三步筛选流程：
  - **可行性筛选**：剔除无法定义明确工件契约（Cᵢ）或可靠评分器（Gᵢ）的任务；
  - **难度筛选**：单步任务用Qwen3.5-27B试跑三次，全部正确则删除；有难度标注的仅保留medium/hard；
  - **代表性筛选**：依据各源基准的类别结构人工选取任务，保持覆盖度但避免某类过度代表。
- 任务形式化定义为：
  - τᵢ = (pᵢ, W₀ᵢ, Tᵢ, Cᵢ, Gᵢ, t_maxᵢ)，即任务指令、初始工作空间、可用工具集、工件契约、任务评分器与时间预算；
  - 工件契约 Cᵢ = {(aᵢ,ⱼ, φᵢ,ⱼ)}，其中φᵢ,ⱼ为对文件内容的有效性谓词；
  - 契约完全满足定义为 Sat(W*, Cᵢ) = Πⱼ 1[∃W*[aᵢ,ⱼ]] φᵢ,ⱼ(W*[aᵢ,ⱼ])。
- **工作负载分类**：沿2×3矩阵组织任务，即输入模态（文本/多模态）与执行形式（单步/多步/多步+工具）的笛卡尔积，形成六个工作负载组：Text-SS、Text-MS、Text-MT、MM-SS、MM-MS、MM-MT。

#### （2）统一共享执行环境（Shared Agent Execution）

- 基于OpenClaw构建共享执行环境，所有模型使用相同的智能体循环、工具接口、工作空间抽象与日志协议，减少异构智能体脚手架对比较的干扰。
- 任务默认工具套件统一开放：含OpenClaw自带工具（文件I/O、shell执行、智能体循环控制原语），以及web_search、web_fetch和9个Clawhub技能（如ontology、self-improving-agent、skill-vetter、Agent Browser、desktop-control、github等）。

#### （3）可靠评分协议（Reliable Scoring）

- **三种评分模式**：根据任务性质在构建时分配：
  - 自动评分（auto）：针对可用规则验证结果的确定性任务；
  - LLM评分（judge）：针对开放式输出或多重语义约束的任务，由固定judge模型依据任务提示、轨迹摘要、最终工件和人工制定的rubric评分；
  - 混合评分（hybrid）：按预设权重 w_auto + w_judge = 1 组合上述两种分数；
  - 最终公式：sₘ,ᵢ = w_auto·s_auto + w_judge·s_judge（hybrid时为加权和，auto和judge模式取对应单项）。
- **基于证据的审计**：发现LLM评分存在“无证据正分”（unsupported positive judgment）问题，设计审计机制：
  - 对所有涉及judge的分数施加确定性后验规则触发预筛选；
  - 命中的案例交由不同模型家族的独立meta-judge复核，核对任务提示、执行轨迹、最终工件、评分rubric与primary judge给出的分数及理由；
  - 若判定整体无证据，任务分数置零，即 s_audit = (1 - hₘ,ᵢ)·sₘ,ᵢ。
  - 共识别5类幻觉模式：rubric泄漏（rubric leakage）、死锁循环（deadlock loop）、伪工具调用轻信（pseudo-tool-call credulity）、超时仍给分（timeout-with-credit）、输出不稳定（output instability），另有元审中发现的rubric泄漏等细分模式。

#### （4）部署导向指标（Deployment-Oriented Metrics）

- **准确率**：报告总体准确率和六个工作负载组准确率；
- **效率指标**：报告平均token消耗与美元成本。成本公式为每任务成本 = (1/10⁶)·Σₖ αₖᵐ·uₖᵐ，其中k涵盖输入、输出、缓存读取、缓存写入四种token类别，α为人每百万token参考价格（取自OpenRouter参考费率）；
- **准确率-成本前沿分析**：分文本与多模态分别绘制Pareto前沿。

### 3. 实验设计

- **数据集/基准**：从22个源基准中筛选出233个任务，涵盖多领域、多能力维度。源基准按工作负载组划分：
  - **Text-SS**（20任务）：LogiQA（逻辑推理）、GPQA（研究生级科学问答）；
  - **Text-MS**（87任务）：AdvancedIF（复杂指令跟随）、Bamboogle（多跳问答）、SimpleQA（短形式事实检索）、LongBench（长上下文）、LexEval（法律评估）、TableBench（表格推理）、FinQA（财务问答）；
  - **Text-MT**（55任务）：DeepSearchQA（深度检索）、WideSearch（广泛检索）、Seal0（检索增强推理）、TerminalBench2（命令行任务）、OpenAgentSafety（智能体安全）、OSWorld（桌面控制）；
  - **MM-SS**（20任务）：SimpleVQA（视觉事实检索）、HLE（人类最后一考，跨学科专家级多模态）；
  - **MM-MS**（26任务）：CharXiv（学术图表理解）、MedXpertQA（医学专家级多模态QA）；
  - **MM-MT**（25任务）：AgentVista（高难度多模态智能体任务）、MMSearch（端到端多模态搜索）、MMSearchPlus（溯源感知多模态搜索）。
- **评估模型**：35个模型，包括23个商业API模型（10个模型家族）与12个本地部署的开源权重模型。
- **评分设置**：主judge使用Qwen3.5-VL-Plus；meta-judge使用Claude-Opus-4.6。
- **对照组设计**：所有模型在同一OpenClaw运行时、默认推理设置、隔离会话与工作空间中运行，保持工具可见性与权限一致。

### 4. 资源与算力

- **本地模型部署配置**：本地开源模型使用vLLM在单张NVIDIA RTX PRO 6000 GPU（96 GB VRAM）工作站的单GPU上服务；

- **商业API推理**：通过OpenRouter接入，无明确计算资源数据；
- **说明**：论文未报告训练时长、各模型总推理时间或精确的总GPU时数，给出的单GPU配置信息仅适用于本地模型的推理阶段。

### 5. 实验数量与充分性

- **实验规模**：总体35个模型×若干任务组合，经过适用性筛选后共7,587次有效模型-任务运行；
- **数据覆盖**：任务矩阵为文本20/87/55，多模态20/26/25，分布在六个工作负载组中；
- **评分审计数据**：在7,587次运行中，3,340次为judge/hybrid调用；审计预筛选出182个疑似幻觉案例，最终确认143个为无证据正分；
- **人为验证**：分层抽样100个执行轨迹，由人类专家独立评分。结果显示，meta-judge修正后的分数与人类分数之间的平均绝对误差（MAE=0.049）约为主judge（0.098）的一半，验证了审计机制的有效性。
- **失败模式分析**：抽样30个分层任务，分析所有模型零分轨迹的失败原因，归纳出6类失败模式（SRU、TUIE、PPPA、FCR、VEB、VCS），由Grok 4.5初步分类后辅以人工审核。
- **充分性评估**：整体而言，实验规模较大，覆盖维度较全面（模态×执行复杂度×部署模式×成本），对比模型谱系广（前沿到轻量开源），且补充了人类一致性验证。局限在于未能穷尽所有局部部署配置（未做量化、多GPU等变体实验）。

### 6. 主要结论与发现

- **顶尖模型因负载而异，模型选择应负载感知**：
  - Claude-Opus-4.8在Text-SS（98.8）、Text-MT（65.3）、MM-MT（61.8）上最强；
  - GPT-5.5在Text-MS（83.6）和MM-SS（90.0）上最佳；
  - Gemini-3.1-Pro在MM-MS（88.5）上夺魁。
- **开源模型具有竞争力但仍存在显著差距**：
  - Qwen3.6-27B为本地最强默认选择（Overall 59.8），已接近部分早期商业模型；
  - 与前沿商业模型相比仍落后约15个百分点；
  - Qwen3.6-35B-A3B（Overall 56.6）作为MoE替代方案可行；
  - 8B/9B小模型在完整agent循环中出现明显不稳定。
- **token消耗与美元成本构成两条不同排序链**：
  - token量最低为GPT-5.4-mini，最高为Gemini-3.5-Flash（约为前者的6–8倍）；
  - 美元成本最低为MiMo-V2.5（文本$0.006），最高为Claude-Sonnet-4.6（$0.436）；
  - 极端位置不一致，MiMo-V2.5 token高但成本低，Claude-Opus-4.6 token较少但成本约为前者的71倍。
- **准确性-成本前沿**：
  - 文本任务中，MiMo-V2.5与MiMo-V2.5-Pro及GPT-5.5构成最优序列，但成本增量远超准确率提升，表明文本任务在$0.02以下已接近饱和；
  - 多模态任务的前沿斜率更陡，成本增长换来更明显的准确率上升，决策需区分对待。
- **LLM裁判幻觉审计**：
  - 审计移除143个无证据正分；API模型与本地模型的幻觉模式显著不同——本地模型以死锁循环和伪工具调用为主，API模型则以超时给分为主；
  - 提示了LLM裁判评分应结合轨迹与工件进行证据校验的必要性。

### 7. 优点

- **部署导向设计**：首次将“部署感知”概念系统化地融入智能体评估框架，从模态与执行形式两个维度组织任务，直接回应实际选型痛点；
- **统一环境控制**：基于同一OpenClaw运行时打破源基准间的环境壁垒，确保跨模型差异可归因于模型能力而非框架兼容性；
- **证据审计机制**：创新地结合确定性后验规则与独立meta-judge复核，能识别并修正LLM评分幻觉，且有人类一致性验证支撑可靠性（MAE减半）；
- **低成本、高覆盖**：在单GPU配置下即可评估本地模型，且本地模型与API模型的对比方式务实合理——不伪装上下文匹配的“同条件能力比较”，而是反映各自部署画像下的端到端表现；
- **细粒度失败分析**：提供6类失败模式的定量分解，为后续能力改进提供具体方向；
- **成本透明化**：公开所有模型的token单价与成本计算方式，增强复现性。

### 8. 不足与局限

- **评估配置单薄**：本地模型一律采用统一的FP16/32K上下文配置与单GPU部署，未探索量化和多GPU等实际部署变体（论文坦言不影响“在特定部署画像下”的结论，但限制了泛化性）；
- **基准构建的主观性**：源基准到工作负载组的映射（φ）依赖“主导模态”与“所需执行形式”的人为判定，可能引入分类偏差；
- **时间跨度与时效性**：论文截稿涉及2026年的前沿模型，基准的一次性静态快照无法持续追踪动态模型能力演化；
- **API—本地对比公平性**：API模型享有较大的有效上下文与生产级推理基础设施，与本地模型的差异是端到端差异而非纯模型能力差异，文中已承认这一点，但读者仍需谨慎解读对比数字；
- **judge选择依赖**：主judge和meta-judge均固定为特定模型，潜在的judge偏好或偏差虽经人工验证削弱，但未完全消除；
- **分析与案例样本局限**：失败模式分析仅抽样30个任务，某些模式的代表性可能不够稳健；
- **成本指标依赖公开定价**：价格随市场动态变化，参考成本并不能直接等价于实际部署成本，尤其是本地自有推理时无边际API成本。
