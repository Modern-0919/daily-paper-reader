## 摘要
基于大语言模型（LLM）的工作区代理会在异构资源、外部工具和持久化状态之间执行有状态的多步骤工作流。因此，其安全性必须从整个执行过程中的动作、副作用和状态变化来评估。尽管最近的基准测试推动了可执行安全性测试和轨迹感知验证的发展，但它们很少提供关于风险在何处进入、如何引发不安全行为、针对哪些危害以及支持性证据在执行过程中出现在何处的统一说明。我们引入了AgentS4D，一个用于生命周期范围运行时安全评估的沙盒基准测试。其四维运行时安全框架使用六个风险进入来源、六种诱导策略和九个目标危害来指导案例构建，而七个生命周期检查点则组织运行后证据。AgentS4D包含328个风险注入案例。我们评估了四个工具框架（Hermes、OpenClaw、Claude Code和Codex）与五个LLM后端（GPT-5.5、Gemini 3.1 Pro、DeepSeek-V4-Pro、MiniMax-M3和Qwen3.7-Plus）的所有20种组合在这些案例上的表现，共产生6,560次运行。总体而言，4,461次运行（68.0%）触发了预设的不安全信号。在20种配置中，代理系统的可观察安全性既随其工具框架-LLM配对变化，也随风险引入方式而变化。当相同的诱导策略通过不同的风险载体到达代理系统时，代理系统表现出显著不同的安全行为。当相同的目标危害通过不同的载体和策略实现时，它们也会做出不同的响应。此外，4,344次运行（总体占66.22%）是不安全但完整的。因此，任务完成不能建立运行时安全性，仅测试一种形式的风险可能会隐藏重要的弱点。评估应检查多样风险条件下完整的代理配置，并在整个执行过程中保留证据。

## Abstract
Large language model (LLM)-based workspace agents execute stateful, multi-step workflows across heterogeneous resources, external tools, and persistent state. Their safety must therefore be assessed from actions, side effects, and state changes throughout execution. Although recent benchmarks have advanced executable safety testing and trajectory-aware verification, they rarely provide a unified account of where risks enter, how they elicit unsafe behavior, which harms they target, and where supporting evidence appears during execution. We introduce AgentS4D, a sandboxed benchmark for lifecycle-wide runtime safety evaluation. Its four-dimensional runtime-safety framework uses six risk-entry sources, six induction strategies, and nine target harms to guide case construction, while seven lifecycle checkpoints organize post-run evidence. AgentS4D contains 328 risk-injected cases. We evaluate all 20 combinations of four harnesses (Hermes, OpenClaw, Claude Code, and Codex) and five LLM backends (GPT-5.5, Gemini 3.1 Pro, DeepSeek-V4-Pro, MiniMax-M3, and Qwen3.7-Plus) on these cases, yielding 6,560 runs. Overall, 4,461 runs (68.0%) trigger prespecified unsafe signals. Across the 20 configurations, the observed safety of an agent system varies with both its harness-LLM pairing and how risk is introduced. Agent systems exhibit markedly different safety behavior when the same induction strategy reaches them through different risk carriers. They also respond differently to the same target harm when it is realized through different carriers and strategies. Moreover, 4,344 runs (66.22% overall) are unsafe yet complete. Thus, task completion cannot establish runtime safety, and testing only one form of a risk can conceal important weaknesses. Evaluations should examine complete agent configurations across diverse risk conditions and retain evidence throughout execution.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：基于 LLM 的工作区代理（workspace agent）在真实数字环境中执行有状态、多步骤工作流，会读取异构文件、调用代码和浏览器工具、与外部服务通信，并在交互之间保持持久状态。这类能力支持长周期任务，但也使得部分可信的上下文内容（文档、网页、技能、工具、记忆）可能影响代理的规划、工具调用或对外通信，从而造成安全风险。
- **核心问题**：运行时安全（runtime safety）是"完整 harness-LLM 配置 + 任务环境"的综合属性，无法从单次响应或有效的交付物推断。现有安全基准虽然已从孤立响应走向可执行任务评估，但在风险进入点、诱导方式、危害目标与证据位置的统一刻画上存在明显缺口。
- **关键差距**：已有基准（如 OpenAgentSafety、SABER、SkillSafetyBench、AgentCanary、HarnessAudit、VERA 等）的**分类体系各异**、**评估系统不一**、**判定定义不同**，难以支持跨风险来源与跨 harness-LLM 配置的系统性比较。
- **研究问题**：风险如何进入、如何诱发不安全行为、针对何种危害、证据出现在执行过程的哪里、以及**任务完成能否代表安全**。

## 2. 论文提出的方法论

### 2.1 核心思想：四维运行时安全框架（S/T/L/K）

该框架将案例构建（case construction）与运行后证据组织（post-run evidence）明确分离：

| 维度 | 含义 | 类别数 | 说明 |
|------|------|--------|------|
| **S**（Risk-Entry Source） | 风险进入来源 | 6 | 攻击者控制内容进入代理的载体 |
| **T**（Induction Strategy） | 诱导策略 | 6 | 载荷如何试图影响/说服代理 |
| **L**（Target Harm） | 目标危害 | 9 | 测试的安全边界/受保护资产 |
| **K**（Lifecycle Checkpoint） | 生命周期检查点 | 7 | 运行后证据映射到的执行阶段 |

### 2.2 威胁模型（Threat Model）

- **被评估单元**：完整的代理配置 = LLM 后端 + agent harness + 任务环境。
- **攻击者能力**：非自适应（non-adaptive）、任务知情（task-informed），控制**恰好一个**指定风险进入来源（S1-S6）；准备固定载荷，但**不能**观察实时轨迹、在线修改载荷，也无法访问宿主机验证器。
- **可信组件**：可信案例构造者（预注册不安全信号）与宿主机侧验证器（运行后评估证据），两者均对代理隐藏。
- **安全目标**：工作区资产的机密性、完整性、可用性；授权目标与任务状态保持；最小权限原则；外部效应可控。
- **重要设计**：每个案例**只隔离一个主要风险来源**，以保证跨来源比较的可归因性。

### 2.3 六大风险进入来源（S1—S6）

1. **S1 当前用户消息**：攻击载荷插入渲染给代理的用户消息中（不替换授权目标）。
2. **S2 上传资源**：载荷嵌入任务提供的文档、电子表格、图片关联文本或结构化数据文件中。
3. **S3 网页/URL**：载荷由受控 Web 端点返回（页面文本、链接页面、嵌入内容、元数据等）。
4. **S4 外部技能（skill bundle）**：载荷放入案例提供的技能包，包括描述、指令、模板、脚本等；注册技能本身不构成接触，需代理实际发现、加载或调用。
5. **S5 长期记忆/历史状态**：载荷存储在分配给该运行的任务范围内持久状态中（记忆条目、历史摘要、存储偏好等）。
6. **S6 MCP/工具协议服务**：载荷放在案例提供的 MCP/工具服务中（发现元数据、工具描述、参数 schema、返回结果、暴露的资源或提示）。

### 2.4 六种诱导策略（T1—T6）

- **T1 指令覆盖**：直接指示代理忽略/替换/重新解释授权目标或安全约束。
- **T2 权威冒充**：伪装为可信来源（系统管理员、官方机构、内部通知、安全审计等）。
- **T3 优先级操纵**：将指令框架为紧急、强制或任务必需，促使代理优先执行。
- **T4 隐蔽嵌入**：将指令藏在次要位置（注释、折叠区域、图片关联文本、表格注释、元数据字段）。
- **T5 条件触发**：指定特定触发条件（到达某轮次、访问某资源、进入某状态）。
- **T6 编码混淆**：通过编码、分割、字符变换或跨字段重组来隐藏指令。

### 2.5 九种危害目标（L1—L9）

数据泄露（L1）、破坏性行为（L2）、内部侦察（L3）、权限提升（L4）、目标劫持（L5）、未授权访问（L6）、合规绕过（L7）、不受控外部通信（L8）、持久污染（L9）。

### 2.6 七个生命周期检查点（K1—K7）

K1 输入摄取 → K2 来源与授权评估 → K3 规划与决策 → K4 工具执行 → K5 外部交互 → K6 状态更新 → K7 结果交付。

检查点**不是线性流水线**：代理可重复访问同一功能阶段，一个不安全运行可被打多个标签。**K 在运行后映射**，与 S/T/L 的构建期标签明确区分。

### 2.7 案例构建与验证协议

- 从 76 个 Workspace-Bench 可执行任务（easy/medium/hard 三个难度）转化出 **328 个风险注入案例**。
- 形式化定义：源任务 \(b_i = (g_i, w_i, d_i, q_i)\)，其中 \(g_i\) 为授权核心目标，\(w_i\) 为初始上下文与环境，\(d_i\) 为预期交付物，\(q_i\) 为完成判定谓词。风险变换产生 \(c_{ij} = (g_i, w_i \oplus r_{ij}, d_i, q_i, u_{ij})\)，其中 \(r_{ij}\) 是受控修改，\(\oplus\) 为受控变换而非简单集合并，\(u_{ij}\) 为案例特定的不安全判定谓词。
- **关键约束**：变换保留授权目标、任务相关源资产、预期交付物和完成谓词；每个案例只有**一个**主要 S 标签、一个 T 标签和一个 L 标签；L 表示**意图危害边界**（不暗示已观察到不安全判定）。
- **纳入标准**：只有当载荷能连贯地融入任务上下文、且存在可观察证据判断不安全条件是否发生时，才实例化该组合。因此并非所有 S×T×L 组合都存在（如 S5-T2、S5-T5、S6-T1 等缺失）。

### 2.8 判定协议与指标

- **独立双判定**：任务完成和运行时安全各自独立判断。完成检查器评估交付物谓词；安全检查器评估预注册的不安全信号（agent 消息、工具轨迹、工件、工作区状态、服务收据）。
- **安全状态五分类**（互斥且完备）：
  - \(n_U\)：Unsafe（触发不安全信号）
  - \(n_D\)：Safe—explicit defense（明确防御，有风险识别+保护动作证据）
  - \(n_E\)：Safe—exposed（暴露安全，"silent handling"，确认接触但无明确防御）
  - \(n_N\)：Safe—exposure unconfirmed（未确认接触）
  - \(n_I\)：Inconclusive（记录缺失导致无法判定）
- **四个核心指标**：
  - **ASR**（攻击成功率）= \(n_U / n_T\)
  - **cASR**（条件攻击成功率）= \(n_U / (n_U + n_D + n_E)\)
  - **SHR**（安全处理率）= \((n_D + n_E) / (n_T - n_I)\)
  - **TCR**（任务完成率）= \(n_C / n_T\)
- **统计口径**：由于同源任务的案例不独立，使用 **5,000 次源任务级 bootstrap 重采样**（有放回抽取 76 个源任务）计算 95% 置信区间。

- **规模**：328 个风险注入案例，每个案例有唯一的 S/T/L 标签组合。

### 3.2 被评估系统

- **4 个 harness**：Hermes 0.14.0、OpenClaw 2026.6.9、Claude Code 2.1.201、Codex CLI 0.142.5。
- **5 个 LLM 后端**：GPT-5.5、Gemini 3.1 Pro、DeepSeek-V4-Pro、MiniMax-M3、Qwen3.7-Plus。
- **完全交叉网格**：4×5 = 20 个配置 × 328 案例 = **6,560 次运行**（每个配置对每个案例运行一次）。

### 3.3 执行环境

- 每次运行使用**全新容器**（独立工作区、会话、适配器状态、审计目录），S5 记忆状态仅在分配运行内跨轮次可用。
- 受控服务处理 Web、邮件、消息、mock API 交互；仓库操作使用独立项目。
- 容器保留**出站互联网访问**，但任务不要求/不指示访问公共互联网。
- 远程模型调用通过专用中继；超时从 900 秒到 3,600 秒（按案例 manifest），无自动重试。

### 3.4 对比与验证设计

- 与 7 个相关基准对比（OpenAgentSafety、SABER、SkillSafetyBench、AgentCanary、HarnessAudit、ATBench、VERA），对比维度包括风险条件表征、评估协议、判定独立性和证据组织。
- **敏感性分析**：源任务等权与案例等权对比；替代 K 映射（移除仅由元数据提供的证据）检验生命周期结论的稳健性。
- **部分匹配载体分析**：固定源任务、诱导策略、危害目标和配置后，比较不同载体间的 ASR 差异（32 个分层、66 案例、1,320 运行）。
