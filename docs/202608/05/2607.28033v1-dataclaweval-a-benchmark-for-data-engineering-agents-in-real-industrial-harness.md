## 摘要
大型语言模型（LLM）及基于LLM的智能体正越来越多地被用于自动化复杂工作流，有望彻底改变数据管理与处理方式。然而，现有基准主要集中在简化的文本到SQL转换或数据分析上，使得端到端数据工程这一关键而复杂的领域在很大程度上尚未被探索。为填补这一空白，我们提出了DataClawEval，这是首个专门用于评估真实数据工程场景中自主智能体端到端任务完成能力的综合基准。它基于专业企业数据工程师编写的生产级代码构建，包含100个严谨的端到端任务，涵盖五种执行引擎：PySpark、MySQL、HiveSQL、PrestoSQL/Trino和FlinkSQL。不同于非确定性的“LLM作为裁判”评分方式，每个任务都在特定于案例的隔离沙箱中执行，并由确定性的基于规则的脚本进行评分。对16个前沿智能体的评估暴露了关键局限：最强模型总体得分仅为74.9，且没有一个模型占据主导地位，因为每个模型在不同的引擎上表现出色，这揭示了严格的领域专门化而非全能精通。因此，自主数据工程仍然是一个艰巨且尚未解决的挑战。我们在https://github.com/Dicemy/DataClawEval/tree/master发布了我们的数据集、容器化环境和确定性评估脚本。

## Abstract
Large language models (LLMs) and LLM-based agents are increasingly being deployed to automate complex workflows, promising to revolutionize data management and processing. However, existing benchmarks predominantly focus on simplified Text-to-SQL translation or data analysis, leaving the critical and complex domain of end-to-end data engineering largely unexplored. To bridge this gap, we introduce DataClawEval, the first comprehensive benchmark designed specifically to evaluate the end-to-end task completion capabilities of autonomous agents in real-world data engineering scenarios. Built upon production-grade code authored by professional enterprise data engineers, it comprises 100 rigorous, end-to-end tasks spanning five execution engines: PySpark, MySQL, HiveSQL, PrestoSQL/Trino, and FlinkSQL. Rather than non-deterministic LLM-as-a-judge scoring, each task is executed within a case-specific, isolated sandbox and graded by deterministic, rule-based scripts. Evaluating 16 frontier agents exposes critical limitations: The strongest model attains only 74.9 overall, and no single model dominates, as each excels on a different engine, revealing strict domain specialization rather than omnipotent proficiency. Thus, autonomous data engineering remains a formidable, unresolved challenge. We release our dataset, containerized environments, and deterministic evaluation scripts at https://github.com/Dicemy/DataClawEval/tree/master

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

- **核心思想**：从真实企业生产代码出发，通过“人机协同”方式重建可识别正确解的任务实例，并让智能体在活沙箱环境内实际运行，以最终生成的“数据产物”（而非仅代码或文本答案）作为评测对象。
- **任务范围**：包含离线批处理（PySpark、HiveSQL、MySQL、PrestoSQL/Trino）与在线流处理（FlinkSQL）两类工作负载；业务域覆盖运维与资源治理、数据分析与用户增长、安全与风控、内容/社区/研发效能、广告与营销五个领域。
- **数据构造流程（五个阶段）**：
  1. **生产代码筛选**：收集真实数据工程代码，脱敏、去重、分层采样，保留多样性与代表性，作为 ground-truth 实现。
  2. **可执行任务规格重建**：利用 LLM 从 ground-truth 代码反推用户意图，合成输入表，形成“自然语言请求 + 输入表 + 参考实现”的初始任务。
  3. **迭代验证（差分测试）**：先执行验证保证 ground-truth 可运行；再由人类专家扰动实现（保持可执行但语义错误），要求输入表能区分正确与错误结果，不能区分则反馈给 LLM 修改任务规格。
  4. **任务级评分脚本开发与验证**：为每个任务定制评分脚本，覆盖模式、数值、业务逻辑等维度；要求 ground-truth 得满分、扰动实现不得满分。
  5. **最终专家审计**：领域专家联合检查意图、输入表、参考实现、评分脚本与预期输出的一致性。
- **评估框架**：
  - **隔离执行**：每个任务在全新 Docker 容器中运行，环境内仅含任务描述和工程工具，智能体需自主探索表结构、理解数据分布、编写并运行程序；结束后在同一容器内自动评分。
  - **产物导向评估（Artifact-oriented）**：不比较代码文本，而是验证生成的数据表/文件，从以下方面打分：可执行性、模式正确性（表名称、列、类型、存储格式）、行级对齐、数值精度、类别/业务标签正确性。
  - **过程导向评估（Process-oriented）**：额外评估执行轨迹，包括探索充分性、执行效率、自我验证行为。
  - **总评分公式**：  
    Score = α·S_artifact + (1−α)·S_process  
    通常取 α=0.7，即更看重最终产物正确性，同时奖励高效可靠的过程行为。

## 6. 论文的主要结论与发现

- **远未饱和**：最强模型 GPT 5.5 平均分仅 74.9，最高与最低模型相差约 14.6 分（60.3–74.9），留有充足区分空间。
- **引擎难度极不均匀**：MySQL 最易（所有模型 >74，最高 88.8）；HiveSQL 最难（最高仅 69.8，部分模型低于 60）；PySpark 与 FlinkSQL 的模型间差异最大，区分能力强。
- **没有单一全能模型**：GPT 5.5 总评最高，但 PySpark 最好的是 Claude Opus 4.8（83.8），PrestoSQL/Trino 最好的是 DeepSeek V4 Pro 与 Gemini 3.5 Flash（77.7，但后者 token 成本高 3 倍），FlinkSQL 最好的是 DeepSeek V4 Flash（85.0）。模型呈现明显的引擎/领域专门化。
- **Token 消耗与质量不相关**：GPT 5.3 Codex 最省 token（271.4k/任务）但排名下半区；Gemini 3.5 Flash 最耗 token（973.8k/任务）但仅中等。高 token 消耗不等于高质量，试错式探索往往低效。
- **规则评分不可替代**：LLM judge 系统性高估所有指标（过程分从 22.2 被高估至 75–76，产品分从 52.1 高估至 90+），稳定性差（单案例标准差最高超 55 分），违反硬性评分上限（最高给出 291% 上限），并对流式语义（FlinkSQL）产生严重双向错误。
- **模型稳定性差异大**：Gemini 3.1 Pro 最稳定（max−min 差距 12.63），Hy3 最不稳定（差距 26.76，pass@3−pass^3 差距达 26.5%）。高峰性能不能代表可靠执行。
- **工具调用频率与性能无关**：高效规划（少调用、高分）与低效试错（多调用、低分）形成明显对比；GPT 5.5、Claude Opus 4.8 等处于“高效区”，而 Kimi 系列、MiniMax M2.7、Hy3 属于“低效区”。
- **低分集中且错误模式多样**：18.2%（292/1600）的运行低于 50 分；HiveSQL 与 PrestoSQL/Trino 低分率最高（26.1% 与 25.5%）；约 1/3 低分是“静默错误”（程序成功写出但结果错误）；超时运行占 4.9%（79/1600），其中 GLM 5.2 超时率 22%，若只看完成任务的均值其实际排名应为最高（82.1）而非报告的第 11 位。

## 7. 优点

- **问题定位精准**：填补了数据工程智能体评测空白，首次覆盖“端到端真实工业数据工程”而非仅 SQL 或分析问答。
- **数据真实性与严谨性**：任务源自生产级企业代码，经过人类

- **数据真实性与严谨性**：任务源自生产级企业代码，经过人类专家与 LLM 协同的五阶段构造流程，包括差分测试、扰动验证和最终专家审计，确保每个任务都有可执行、可判别的 ground truth，且评分规则能有效区分正确与错误解。与纯合成数据或简化竞赛题不同，DataClawEval 的任务带有真实业务语义和工业级复杂度。
- **评测设计的工程化视角**：采用“产物导向 + 过程导向”双维评估，强调最终数据产物的正确性而非代码文本相似度，同时兼顾执行轨迹的效率与探索质量。这种设计更贴近真实数据工程师的考核标准——结果对、过程稳、成本可控。
- **覆盖面广**：5 种执行引擎（含流批两类）、5 个业务域、中英双语、100 个任务，在同类基准中覆盖面最广；统一 agent 脚手架和隔离 Docker 环境保证了跨模型比较的公平性。
- **分析深度突出**：论文不仅给出平均分排名，还系统性地做了稳定性分析（重复运行）、judge 可靠性检验、token 效率分析、错误分类、超时归因等，试图从多个维度解释“为什么某个模型更强/更弱”，而不仅仅是报告排名。
- **关键负面发现价值高**：对 LLM-as-judge 的严格评估揭示了其系统性高估、违反硬性上限、对流式语义判断混乱等问题；对工具调用频率的分析揭示了低效试错与静默失败的普遍性。这些发现对整个 LLM 评估社区具有警示意义。

## 8. 缺点与局限性

- **算力与成本信息披露不足**：论文未给出 GPU 型号、数量、总运行时长、API 调用费用等关键资源指标。考虑到 1600+ 次完整智能体运行及多次重复实验，其总成本可能相当可观，但读者无法据此判断该基准的可复现成本与部署门槛。
- **引擎间任务量不均衡**：PrestoSQL/Trino 仅 12 个任务，在所有引擎中最少；HiveSQL 28 个、FlinkSQL 20 个。少量任务上的模型差异可能受单任务难度波动影响，引擎级结论的统计稳健性存疑。
- **中英文子集并非平行翻译**：50 个英文任务与 50 个中文任务来自不同的生产代码，语言与任务难度两个变量混杂，双语性能对比的结论不够干净。
- **单一 agent 脚手架**：所有评测仅使用腾讯 CodeBuddy 一种 agent 框架，模型以外的工具选择、提示词模板、重试策略等都被固定。真实场景中，agent 框架本身对表现影响极大，本基准无法回答“最优模型 + 最优框架”的组合问题。
- **单次运行的随机性**：除 4 个模型外，其余 12 个模型均只有一次主实验运行结果；即便有稳定性实验，也只能说明少数模型在重复运行下的波动范围。若某些模型存在高方差，单次结果可能误导排名。
- **多轮人工反馈缺失**：真实企业数据工程中，智能体通常会与工程师进行多轮交互、接收临时需求变更和纠错反馈；本基准的任务均为一次性独立完成，未纳入人机协作环节，因此结果反映的是“零交互自主能力”而非实际部署表现。
- **任务/评分脚本的开放性问题**：论文正文未明确说明数据集、评分脚本、agent 脚手架是否完整开源及许可条款。若不做充分开放，后续学术社区难以独立复现、扩展或公平比较。

## 9. 总体评价与个人见解

- **总体定位**：DataClawEval 是数据工程智能体评测领域的一个重要里程碑。它首次将“真实工业数据工程的端到端能力”作为评测对象，在任务真实性、评估全面性和分析深度上显著优于现有基准。论文提出的差分测试+专家审计任务构造流程，以及产物+过程双维度评估框架，都有较强的普适参考价值，可迁移到其他垂直领域（如金融数据分析、科学计算工作流）的智能体评测。
- **对社区的核心贡献**：与其说它提供了“哪个模型最强”的答案，不如说它提供了“如何可靠地评测数据工程智能体”的方法论，并揭示了三个容易被忽视的问题——LLM judge 在复杂数据任务上不可信、高 token 消耗不等于高质量、模型稳定性差异可能超过平均分差异。这些发现在工业部署选型（如选择 FlinkSQL 任务的模型）和后续研究（如开发更可靠的自动化评估器）中具有直接指导意义。
- **未来可扩展方向**：引入多轮人机协作和交互式纠错评估；扩展到更多引擎与数据源（如 ClickHouse、Kafka 流处理、dbt 转换）；探索自适应 token 预算或成本敏感评分；将任务生成流水线自动化并持续扩充数据集；结合数据血缘和可观测性指标做更深层次的过程评估。
- **总体判断**：这是一篇方法严谨、洞察丰富、工程实现扎实的高质量基准论文。虽然存在任务量不均、资源披露不足、单一框架评测等局限，但就其所解决的问题和提供的数据价值而言，完全称得上该细分领域的开创性工作。强烈建议后续研究者在其基础上建立更开放的评测生态。
