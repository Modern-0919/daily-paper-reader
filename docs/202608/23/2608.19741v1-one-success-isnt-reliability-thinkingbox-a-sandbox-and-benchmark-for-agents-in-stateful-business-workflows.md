## 摘要
近期智能体基准测试越来越倾向于在可执行环境中进行评估，涵盖代码修复、网页导航、应用API和函数调用等任务。然而，完成代码之外的重要工作不仅需要生成看似合理的回答或有效的工具调用：智能体必须在多轮交互中收集缺失信息、遵循领域策略、协调依赖工具，并实现正确的持久状态转换而不产生附带影响。在本文中，我们介绍了Thinkingbox，一个用于工具-智能体-用户交互的沙盒，提供隔离的MCP兼容工具会话、完整的执行轨迹以及终端后端状态的结果评估。基于该沙盒，Thinkingbox-bench包含507个受策略约束的工作流，涵盖零售、酒店、汽车保险、新型银行内部IT以及咨询IT/HR支持等多个场景。每次尝试通过任务特定的可执行检查进行评估，接受有效轨迹，同时拒绝错误、缺失或额外效果；指定任务还会额外检查最终回复的必要属性。在专有模型和开放权重模型中，最强模型达到了65.36%的pass@1，但仅25.25%的pass^20。此外，许多失败的试验表现出干净的终止和有效的状态变更操作，表明响应或工具调用级别的信号无法清晰代表端到端任务的完成情况。Thinkingbox-bench揭示了偶尔找到成功轨迹与可靠完成有状态业务任务之间的巨大差距。我们同时发布了Thinkingbox和Thinkingbox-Bench：https://github.com/microsoft/thinkingbox

## Abstract
Recent agent benchmarks increasingly ground evaluation in executable environments, from code repair to web navigation, app APIs, and function calling. Yet completing consequential work beyond code requires more than producing a plausible response or valid tool call: agents must gather missing information over multiple turns, follow domain policies, coordinate dependent tools, and realize the correct persistent state transition without collateral effects. In this paper, we introduce Thinkingbox, a sandbox for tool-agent-user interaction that provides isolated MCP-compatible tool sessions, complete execution traces, and outcome evaluation over terminal backend state. Built on this sandbox, Thinkingbox-bench contains 507 policy-conditioned workflows across numerous scenarios, including retail, hospitality, auto insurance, neobank internal IT, and consulting IT/HR support. Each attempt is evaluated by task-specific executable checks that accept valid trajectories while rejecting wrong, missing, or extra effects; designated tasks additionally check required properties of the final response. Across proprietary and open-weight models, the strongest achieves 65.36% pass@1, but only 25.25% pass^20. Moreover, many failed trials show clean termination and valid state-changing actions, showing that response or tool-call-level signals are not clear proxies for end-to-end task completion. Thinkingbox-bench reveals a large gap between occasionally finding a successful trajectory and reliably completing stateful business tasks. We release both Thinkingbox and Thinkingbox-Bench: https://github.com/microsoft/thinkingbox

- **研究动机**：现有 LLM 智能体基准逐步转向可执行环境（代码、网页、函数调用），但多数只评估“单次响应或单次工具调用是否正确”，无法反映智能体在真实业务中“可靠完成多步、有状态、有后果的工作”的能力。
- **核心问题**：状态型业务工作流（如改订单、处理退款、更新保险理赔、路由内部服务请求）要求智能体在多个轮次中收集缺失信息、遵循领域策略、协调依赖工具、正确修改持久化后端状态，并避免附带副作用。一次成功轨迹并不等于可靠完成。

## 2. 方法论

- **核心思想**：将工具–智能体–用户交互封装为可重置、可隔离、可验证的沙盒环境，使相同循环同时支持推理评估、排行榜评测和失败分析。
- **任务形式化**：每个任务定义为 \(x=(b_0, g, T, U, C)\)，其中：
  - \(b_0\)：初始后端状态；
  - \(g\)：用户目标；
  - \(T\)：可用领域工具集（MCP 兼容）；
  - \(U\)：模拟用户策略；
  - \(C=\{c_i\}\)：隐藏的可执行检查集合。
- **POMDP 建模**：任务诱导有限时域 POMDP \(M_x=(S_x,A_x,O_x,P_x,Z_x,R_x,\mu_x,H)\)，潜在状态 \(s_t=(b_t,z_t,\ell_t,q_t)\) 包含后端状态、模拟用户私有状态、事件日志和回合状态；智能体只能通过可观测历史行动，奖励在终态由可执行判定给出。
- **判定公式**：最终结果 \(V(x,\rho)=\prod_i c_i(s_T,e,\rho)\)，合取式判定——所有条件必须同时满足；副作用 \(e=\Delta_x(s_0,s_T,\rho)\) 为任务定制提取的状态变化。
- **沙盒机制**：
  - 每次尝试独立重置到相同初始状态，防止跨尝试共享数据库行或缓存；
  - 提供隔离的 MCP 工具会话，工具调用真实执行；
  - 完整记录轨迹，支持失败诊断和训练奖励。
- **基准构建**：三阶段流程——工作流设计（五领域模板）→ 可执行任务实例化（后端状态、工具、用户策略、检查器）→ 自动+人工验证过滤（移除工具损坏、歧义、不可验证任务）。

## 6. 主要结论与发现

- **整体性能有限**：最强模型 GPT-5.4 的 pass@1 仅 65.36%，pass@20 达 91.12%，但 pass^20 仅 25.25%——即找到一次成功不难，但 20 次全部成功极难。
- **发现–可靠性差距明显**：多个模型 pass@20 很高（如 GPT-5.4 84.81%、DeepSeek-V4-Pro 84.62%），但 pass^20 很低（8.68%、3.55%），说明智能体能“发现”正确轨迹但无法“稳定重复”。
- **领域差异巨大**：零售最易（平均约 52% pass@1），汽车保险最难（平均约 23%）；强模型并非所有领域都强，例如 GPT-5.2 在零售 70% 但保险仅 22%。
- **失败模式**：
  - 工具使用错误占失败主导（平均 77.5%），尤其是未能从工具错误中恢复；
  - 错误状态更新占 12.1%——工具调用成功但状态改变错误；
  - 不完整用户解决占 7.9%；
  - 无状态变更动作仅占 2.5%。
- **表面信号不可靠**：80.88% 的失败试验既“干净终止”又调用了状态变更工具，67.24% 甚至无显式工具错误，说明仅靠响应或工具调用级指标会严重高估完成率。

## 7. 优点

- **沙盒设计通用且可复用**：统一的工具–智能体–用户交互循环，既可用于评估，也可产出奖励用于训练。
- **以状态和副作用为中心**：可执行检查能拒绝错误的、缺失的或额外持久效果，允许不同有效轨迹获得同等奖励。
- **隔离与可重复**：每次尝试独立重置，避免跨尝试污染；MCP 兼容工具贴近实际部署。
- **完整的轨迹与失败分析**：提供真实轨迹示例，并用确定性规则分类失败模式，可解释性强。
- **可靠性视角**：通过 pass@k 与 pass^k 区分“可发现性”和“可重复性”，比单次 pass@1 更贴近真实部署需求。
- **领域多样**：覆盖零售、旅行、保险、银行、咨询等多个业务模式，提升泛化参考价值。

## 8. 不足与局限

- **判定范围受限**：507 个任务中 477 个仅检查后端状态，不评估用户沟通质量，可能出现“状态正确但向用户错误汇报”仍算成功的情况。
- **任务合成性**：基于非公开源数据合成重建，不代表真实企业工作分布；每个任务仅一个黄金终态，排除了多种合理解决方案。
- **模拟用户偏差**：固定使用 GPT-5.4-mini，且模拟用户从不记错、不改变目标、保持配合，无法测试智能体处理难缠用户的鲁棒性；模拟器与最强评估模型同属一个模型家族，可能存在同族交互风格偏好。
- **验证充分性不足**：未对模拟用户敏感性、不同终止条件、不同 token 上限做系统消融。
- **资源信息缺失**：未报告 GPU 算力、训练时间等资源细节，影响可复现成本估计。
- **模型与时点局限**：所有结果依赖当前一代模型，快速迭代后结论可能变化。
