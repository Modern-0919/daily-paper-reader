## 摘要
当前对计算机使用智能体的评估分为长时程工作流基准与原子级GUI接地测试。这留下了一个缺乏工具化的中间层：以组件为中心的真实交互（例如，切换按钮组），这些交互足够短以用于诊断，又足够丰富以捕捉现代界面的负担。我们提出了ComponentBench，一个用于在现代Web UI上对计算机使用智能体进行组件级评估的基准与诊断流水线。ComponentBench围绕一个与库无关的97个典型UI组件本体进行组织，这些组件在广泛使用的组件库中被实例化为2,910个经程序化验证的任务，并配以清理后的人类参考轨迹，从而能够对任务成功率和交互效率进行评估。除任务收集外，我们还引入了一个可扩展的流水线，用于在实现后审计实际的结构难度，并跨任务和组件族综合结构化失败分析。我们评估了七个模型——GPT-5.4、Gemini 3 Flash、GPT-5.4 mini、GPT-5 mini、Gemini 3.1 Flash-Lite、Qwen3-VL-235B和UI-TARS-1.5-7B——跨越四种观察与动作空间，结果表明这些设计选择对性能有至关重要的影响。在单个共享测试平台中，仅改变观察与动作空间就会使同一模型的任务成功率变化超过30%：GPT-5 mini从使用可访问性树观察时的83.1%下降到仅使用坐标像素控制时的48.9%。此外，即使最快的配置所耗时间也是匹配的人类参考的3.7倍，而且对人类而言微不足道的空间操作仍然对当前智能体构成挑战。

## Abstract
Current evaluation of computer-use agents is split between long-horizon workflow benchmarks and atomic GUI-grounding tests. This leaves an under-instrumented middle layer: realistic component-centered interactions (e.g., toggle a button set) that are short enough to diagnose and rich enough to capture the burdens of modern interfaces. We present ComponentBench, a benchmark and diagnostic pipeline for component-level evaluation of computer-use agents on modern web UIs. ComponentBench is organized around a library-agnostic ontology of 97 canonical UI components instantiated as 2,910 programmatically verified tasks across widely used component libraries, paired with cleaned human reference trajectories that enable evaluation of both task success and interaction efficiency. Beyond task collection, we introduce a scalable pipeline for auditing realized structural difficulty after implementation and synthesizing structured failure analyses across tasks and component families. Evaluating seven models -- GPT-5.4, Gemini 3 Flash, GPT-5.4 mini, GPT-5 mini, Gemini 3.1 Flash-Lite, Qwen3-VL-235B, and UI-TARS-1.5-7B -- across four observation and action spaces, we show that these design choices critically impact performance. Within a single shared harness, changing only the observation and action space shifts task success by more than 30% for the same model: GPT-5 mini falls from 83.1% with accessibility-tree observations to 48.9% with coordinate-only Pixel control. Moreover, even the fastest configuration takes 3.7x as long as the matched human reference, and spatial manipulations that are trivial for humans continue to challenge current agents.

## 1. 核心问题与整体含义

- **研究背景**：当前计算机使用智能体（computer-use agents）的评估存在两个极端——长时程工作流基准（如 WebArena、VisualWebArena、OSWorld）虽然任务真实，但失败归因困难；原子级 GUI 接地基准（如 ScreenSpot）仅测试定位能力，无法覆盖真实组件所需的多步交互。
- **核心问题**：两者之间缺失一个"中间层"——以真实 UI 组件为中心、足够短以支持诊断、又足够复杂以反映现代界面负担的交互评估。长任务的实际可靠性受限于其中每个组件交互的可靠性：若 5 个关键交互各自达到 80% 成功率，端到端成功率上限仅约 33%。
- **整体含义**：本文提出 ComponentBench，填补了这一空白，从组件层面定位智能体的失败根源，为提升部署中的效率与可靠性提供可操作诊断，而非仅提供排行榜式评分。

## 2. 方法论

- **组件本体**：基于 WAI-ARIA APG 规范与六种主流 React 组件库（Ant Design、MUI、Mantine、Fluent UI、Chakra UI、Headless UI）的组件清单，构建了**97 个典型组件类型**、**14 个交互家族**、**24 个任务模板**的跨库无关本体。
- **任务规模与实现**：主要基于 Ant Design、MUI 和 Mantine 三个库，实例化为 **2,910 个程序化验证任务**（另有 30 个 markdown 编辑器任务使用外部实现）。每个任务以 YAML 规格定义，包含典型类型、实现来源、任务模板、场景上下文（8 个受控因素：主题、间距、布局、位置、缩放、实例数、引导、杂乱度）、预期难度（7 个概念轴）、成功触发器与负例。
- **LLM 辅助构建流程**：GPT-5.2 Pro 生成任务规格 → Claude Code 实现为真实可交互的 Next.js 页面 → 人类操作员执行两次并清理记录，保留较短通过轨迹作为参考。
- **程序化验证**：每个任务都有独立的 JavaScript 检查器，验证提交后的最终状态（而非中间选择）；负例确保邻近的但不正确的状态不计为成功。验证器状态与智能体观察隔离，目标值和成功谓词存放在 React 闭包中，不暴露为 DOM 属性或页面文本；MutationObserver 实时剥离所有 test-only 属性。
- **四种观察/动作空间**：① AX-tree（截图+可访问性树文本，通过元素 ID 操作）；② Set-of-Marks（截图+编号叠加，通过元素 ID 操作）；③ Pixel（仅截图，通过坐标操作）；④ Browser-Use（独立的 browser-use 框架，具备 DOM 序列化信息与接地元素，每步最多 4 个原始动作）。前三者共享同一 BrowserGym 基础设施，仅改变观察与动作方式；Browser-Use 是工具丰富的参考模式。
- **预期难度 vs 实现难度**：预期难度在生成时标注（7 个概念轴）；实现难度通过重放人工轨迹，提取 24 维结构特征向量（目标尺寸、间距、叠加深度、选项密度等），聚合约到同 7 个轴，区分"设计意图"与"实际呈现的难度"。
- **诊断流水线与 Core 蒸馏**：三层流水线（任务数据包组装 → 任务级观察 → 组件级报告），将任务、轨迹和模型运行转化为可复用证据；基于实现难度审计和诊断报告蒸馏出 **ComponentBench-Core**——912 个重新生成的困难任务，集中于尚未解决的关键交互族。

## 3. 实验设计

- **评估模型**：7 个模型——Gemini 3 Flash、Gemini 3.1 Flash-Lite、GPT-5.4、GPT-5.4 mini、GPT-5 mini、Qwen3-VL-235B（开源权重 VLM）、UI-TARS-1.5-7B（7B 开源 GUI 交互模型，采用原生 Pixel 测试框架）。

- **评估维度**：不仅评估最终成功率，还评估**步骤效率**（≤H/≤2H/≤3H/≤5H，即人类步数的 1/2/3/5 倍内完成比例）、**墙钟时间效率**、按组件家族和任务模板的分解表现。

## 5. 实验数量与充分性

- **实验规模**：主实验覆盖 7 个模型 × 4 种观察/动作空间（UI-TARS 仅原生 Pixel 模式），成功率实验共 25 个模型–模式组合，每个组合评估 2,910 个任务。另有失败轨迹分析（8,864 条失败轨迹，5 个模型）、效率分析（步骤×时间）、家族级分解、场景因素分析、Core 压力测试（含 Opus 4.6 的 Pixel 模式）。
- **消融与稳定性验证**：① 重复运行研究——在 278 任务子集上对 4 个模型的 2 个关键模式各运行 2 次，最大偏差 ≤1.4%；② 人类参考轨迹验证——增加 2 名标注者对 278 任务子集进行独立录制，人类间行为差异（1.05×）远小于智能体–人类差距（1.27–3.02×）；③ 难度轴验证——预期难度轴与失败率的 Pearson 相关性分析。
- **充分性评估**：实验覆盖面广，对比设计较公平（前三模式共享同一基础设施，仅改变观察/动作方式；Browser-Use 被明确标注为工具丰富参考模式而非严格对比）。失败分类学采用确定性轨迹特征与 LLM 诊断双标注互补，并经过对抗性人工审查。不足在于：每个模型–模式组合仅一次确定性运行（虽有子集重复验证），以及 Browser-Use 步骤定义与其他模式不对等（每步最多 4 个动作），效率比较偏乐观。

## 6. 主要结论与发现

- **观察/动作空间是关键因素**：同一模型仅改变观察与动作空间即可造成超 30% 的成功率差距——GPT-5 mini 在 AX-tree 下为 83.1%，在 Pixel 下仅 48.9%。
- **SoM 红利因模型而异**：对较弱模型帮助显著（GPT-5 mini +29.6%），但对 GPT-5.4（−6.8%）和 GPT-5.4 mini（−2.4%）反而有轻微副作用——结构化叠加对已擅长直接视觉交互的模型可能成为噪音和干扰。
- **效率是部署瓶颈**：即使最快的配置（GPT-5.4 mini SoM）平均耗时仍为人类的 3.7 倍；最慢的（GPT-5 mini Pixel）达 21.5 倍，平均每个成功任务耗时 71.8 秒。最强模型在人类步数预算内完成的任务比例远低于最终成功率。
- **空间操作是短板**：对人类仅需 1–2 步的操作（滑块、拖放列表、分割器等 9 种组件），所有智能体的平均通过率低于 60%，如可调整列宽（24.4%）、窗口分割器（38.3%）、范围滑块（39.9%）。不存在反向反转（人类困难而智能体容易的组件）。
- **失败机制可分类**：基于 8,864 条失败轨迹的确定性分类学揭示高频失败机制——连续校准误差（20.2%）、瞬态状态丢失（19.9%）、缺少提交/确认（11.6%）、目标获取/错误实例（11.2%）、重复无进展循环（11.2%）、缺少组件专属程序（9.6%）。约 55.8% 的失败轨迹以重复动作循环结束，但循环是症状而非根因（各机制内 48–67% 均以循环收尾）。
- **视觉上下文具差异化影响**：中杂乱度使 Pixel 模式下降 14.3% 而 AX-tree 仅下降 0.2%；紧凑间距使 Pixel 下降 13.6% 而 AX-tree 下降 4.5%。123 个任务在 AX-tree 中稳定通过却稳定失败于 Pixel，反向不对称仅 52 个。
- **Core 压力测试有效**：Core 上各模型通过率下降 10.7–39.4%；Opus 4.6 在 Core Pixel 达 65.4%（最强像素结果），但仍有三成以上任务未解决、仅 34.1% 在人类步数预算内完成——Core 对前沿模型仍具挑战性。

## 7. 优点

- **组件级可诊断定位**：以单组件为锚点设计任务，使失败根源可追溯到具体交互机制（而非长任务的模糊归因），并通过失败分类学提供了机制级可操作证据。
- **程序化验证的严谨性**：所有任务均有确定性验证器检查提交后的最终状态，负例明确枚举，验证器状态与智能体观察完全隔离，杜绝了 DOM 属性作弊和中间状态误判。
- **人类参考轨迹的多重用途**：既作为任务可解性和保真性的质量控制，又作为效率评估的基准，还作为实现难度审计的遍历预言机。
- **四种观察/动作空间的同框架比较**：前三模式共享同一基础设施仅改变观察与动作方式，实现了对"观察/动作空间影响"的干净归因；对 Browser-Use 的工具丰富性有明确定位，不进行误导性的对等比较。
- **预期难度与实现难度的区分**：通过回放审计区分"设计意图"与"实现现实"，增强了基准的可信度与诊断力。
- **Core 压力测试的设计**：基于证据而非随机子集蒸馏出硬任务套件，能够区分前沿模型水平的差异，避免天花板效应。

## 8. 不足与局限

- **应用范围有限**：仅覆盖 Web（Next.js/Chromium），不涵盖桌面或移动端；仅针对 WAI-ARIA 和三个主要库的常见组件族，不覆盖所有定制插件；明确排除 CAPTCHA 类任务。
- **不评估长时程规划**：仅衡量组件级能力，不直接验证组件级得分对端到端工作流成功率的预测能力——论文自认此为未来工作。
- **人类参考轨迹的标注偏差**：主参考轨迹来自单标注者的两次记录，虽经两名额外标注者的验证子集确认偏差较小（1.05×），但不构成人类最优性的证明；具备树或 DOM 工具的智能体可能存在更短的非视觉路径，效率比较有偏差风险。
- **LLM 辅助构建的生成规律**：任务规格由 GPT-5.2 Pro 生成、页面由 Claude Code 实现，可能存在生成器特定规律；论文未对数据污染进行彻底审计。
