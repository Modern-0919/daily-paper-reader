## 摘要
在生产环境中部署的大型语言模型（LLM）智能体面临一个根本性矛盾：智能体的行为在部署时被固定，而它必须处理的业务规则和边缘情况却在持续演化。现有方法解决了智能体构建和一次性评估问题，但缺乏在不修改智能体源代码的情况下进行持续部署后行为纠正的结构化机制。市场上提供的大多数方法需要大量收集日志和追踪信息，并由工程团队重新审查智能体设计，这一过程繁琐、漫长，且削弱了智能体转型的经济价值。我们提出Agent Gym，一个模块化、领域无关的框架，将任何现有的基于LLM的智能体包裹在一个持续的评估-演化循环中。该框架提供六种可组合的能力——行动（Act）、评估（Evaluate）、调查（Investigate）、纠正（Correct）、学习（Learn）和观察（Observe）——并组织在三个架构区域中：一个将领域知识编码为配置工件的基础层（constitution layer），一个将行动、调查和自适应纠正串联起来的运行时推理流水线，以及一个使领域专家能够通过自然语言交互发现并验证新纠正规则的学习循环。关键技术贡献包括：一个混合确定性-LLM纠正引擎（含21个条件运算符和三层动作）、一个用于无真值合规性验证的三层调查架构，以及一个在人工批准前保证规则正确性的程序化安全循环。我们进一步引入规范到注释差距（Spec-to-Note Gap），一种受自编码器启发的智能体系统透明度视角。一个用于发票处理的开源参考实现表明该框架完全可运行并已准备好被采用。

## Abstract
Large Language Model (LLM) agents deployed in production environments face a fundamental tension: the agent's behavior is frozen at deployment time, while the business rules and edge cases it must handle continue to evolve. Existing approaches address agent construction and one-time evaluation but provide no structured mechanism for continuous post-deployment behavioral correction without modifying the agent's source code. Most of the approaches offered in the market, require intense collection of logs and traces, and re-examining the agent design by the engineering team, a process which is heavy, long and negates the economical value of agentic transformation. We introduce Agent Gym, a modular, domain-agnostic framework that wraps any existing LLM-based agent in a continuous evaluation-and-evolution loop. The framework provides six composable capabilities --- Act, Evaluate, Investigate, Correct, Learn, and Observe --- organized across three architectural zones: a constitution layer that codifies domain knowledge in configuration artifacts, a runtime inference pipeline that chains acting, investigation, and adaptive correction, and a learning loop that enables subject matter experts to discover and validate new correction rules through natural language interaction. The key technical contributions include a hybrid deterministic-LLM correction engine with 21 condition operators and three-tier actions, a three-layer investigation architecture for ground-truth-free compliance validation, and a programmatic safety loop that guarantees rule correctness before human approval. We further introduce the Spec-to-Note Gap, an autoencoder-inspired view of agentic system transparency. An open-source reference implementation for invoice processing demonstrates that the framework is fully operational and ready for adoption.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **静态智能体困境（Static Agent Dilemma）**：LLM 智能体在部署时行为被冻结，但其运行环境中的业务规则、边缘案例和法规异常却在持续演化。这种根本性矛盾导致三类生产环境中的典型失败：
  - **边缘案例失败**：智能体遇到训练数据中未出现的文档配置或监管例外；
  - **系统性误解**：智能体在整个案例类别中持续错误地应用某条业务规则；
  - **漂移与规则演化**：业务规则随时间变化，而智能体无法在不修改代码的前提下吸收这些变化。
- **现有方案的不足**：
  - 主流智能体框架（ReAct、LangChain、AutoGen 等）只解决"构建"问题，缺乏部署后行为演化的结构化机制；
  - 传统评估方法（HELM、AgentBench、SWE-bench 等）依赖静态测试集和真值标注，无法覆盖生产环境中没有真值的新颖案例，也无法衡量细粒度业务规则的合规性；
  - 从"SME 发现问题"到"工程师修改代码"的传统路径涉及软件工程瓶颈——低效、有损、易错且难以规模化；
  - 市场上的事后修正常需要大量日志收集与工程团队重新审查，过程沉重漫长，削弱了智能体转型的经济价值。
- **核心需求**：一种不修改智能体源代码、不依赖训练/微调，能够让领域专家直接参与、在部署后持续评估和纠正智能体行为的轻量机制。

## 2. 论文提出的方法论

### 2.1 总体架构：三个架构区域与六项能力

Agent Gym 将框架组织为三个架构区域，提供六项可组合能力（Act、Evaluate、Investigate、Correct、Learn、Observe）：

- **Zone 1 — 宪法层（Constitution Architecture）**：由两个声明式配置工件构成——
  - **Master Data（YAML）**：涵盖文档类型、提取模式、分类法、验证管道定义、输出模式、评估比较组等 11 个部分的领域完整描述，是唯一的领域事实来源；
  - **Rules Book（Markdown）**：人类可读的完整业务规则文档，描述每个验证步骤、阈值、拒绝模板和决策结果。
  - 该层是领域知识编码层，也是实现"领域无关"的关键：适配新领域只需更换配置工件，框架代码不动。
- **Zone 2 — 运行时推理管道**：三个顺序阶段——**Acting Agent**（受观测的现有智能体，黑盒）→ **Investigation Agent**（依据宪章验证合规性）→ **ALF 引擎**（应用学习到的纠正规则）。
- **Zone 3 — 学习与演化循环**：领域专家（SME）通过自然语言与 Rule Learning Agent 对话，发现错误模式、验证新纠正规则。

### 2.2 核心技术：调查代理（Investigation Agent）

三层验证架构，用于**无需真值（ground-truth-free）的合规性验证**：

| 层 | 方法 | LLM 使用 | 范围 |
|---|---|---|---|
| 1 | 确定性检查（数据源验证、旁路检测） | 无 | 逐字段 |
| 2 | LLM 规则发现（初始化时对规则书做规则分组与缓存） | 有（按内容哈希缓存，首次后摊销为零） | 全局 |
| 3 | 保守交叉验证（三重检查，仅三次独立运行均判违规才报告） | 有（每规则组） | 按组 |

- 合规分数：Fully_Compliant（≥80%）/ Partial_Violation（60–80%）/ Major_Violation（<60%）；重大违规将中止管道。
- 成本控制机制：内容哈希缓存、章节过滤上下文（只发送规则书相关段落）、批量分组（确定性规则组合并为单次调用）、三重检查早期退出。

### 2.3 核心技术：ALF 纠正引擎（Adaptive Learning Framework）

- **检测与纠正分离**：检测完全确定性，纠正按需使用 LLM。
  - 检测：21 种条件运算符（相等、包含、正则、数值比较、列表成员、空值检查、前缀匹配、动态字段引用等），AND 逻辑连接，无 LLM 参与，结果可复现；
  - 纠正：三层动作模型——Tier 1（确定性字段编辑，已知常量）、Tier 2（LLM 手术式补丁，修复特定字段）、Tier 3（LLM 管道继续，适用于智能体提前终止的情况）。
- **Collect-Plan-Execute 流水线**：收集所有匹配规则 → 按层合并为修订计划 → 按固定顺序执行（Tier 3 → Tier 2 → Tier 1）。基于作用域的互斥保证每个作用域最多触发一条规则，每案例最多 2 次 LLM 调用。每次纠正均保留完整审计痕迹。

### 2.4 核心技术：程序化安全循环（Programmatic Safety Loop）

- 以**代码而非提示词**强制实现（LLM 无法绕过），每个候选规则在 SME 批准前经历迭代验证循环（最多三轮）：
  1. **Schema 验证**：规则 JSON 结构是否符合 ALF 模式；
  2. **目标匹配验证**：规则必须在目标案例上匹配，否则 LLM 自动拓宽条件（保持保守）；
  3. **副作用评估（Collateral Assessment）**：对案例样本做确定性评估，若有意外匹配，LLM 自动添加收窄条件（供应商名称、金额范围、服务类别等）予以消除；三轮后仍有副作用则带警告呈交 SME。
- 规则持久化需 SME 明确批准，某些情况下还可配置两级审批（管理员/高级经理二次批准）。

### 2.5 Spec-to-Note Gap：自编码器视角的系统透明度

- 将智能体系统生命周期类比为**自然语言上的自编码器**：
  - 规范（Specification，自然语言）→ 编码（Encode）→ 实现（Implementation，代码/系统，即潜在表示）→ 检查（Inspect）→ 透明度注释（Transparency Note，自然语言，由 LLM 审计器生成）→ 解码（Decode）；
  - 规范与透明度注释之间的差异即"重构损失"，可暴露缺失能力、非预期蔓延（scope creep）和评估套件未覆盖的行为。
- 将 round-trip correctness（Allamanis et al., 2024）从函数级一致性推广至全系统粒度；连接 Self-Refine/Reflexion 与传统 Model Cards/Datasheets 传统。

## 6. 论文的主要结论与发现

- Agent Gym 通过将**纠正放在独立的下游层**而非修改智能体本身，解决了静态智能体困境：原始输出被保留、纠正输出并列存储，审计性和独立回滚得以保障。
- **混合确定性-LLM 纠正引擎**的价值在于分离"可靠检测"与"灵活纠正"：确定性检测保证可复现性，LLM 动作提供超出纯规则引擎的语义理解能力。
- **程序化安全循环**以代码强制（而非提示词约束）保证规则正确性，结合 SME 审批，形成不可绕过的人类治理闭环。
- **宪法治理模型**使领域知识同时充当人类可读文档与机器可解析规范，且宪法与智能体之间存在**双向关系**：宪法既能治理既有智能体，也能作为构建新智能体的规范（constitution → code → refined constitution 的反转流程）。
- **Spec-to-Note Gap** 为智能体系统透明度提供了一个受自编码器启发的原则性框架，可连接自动文档生成与规范-实现一致性诊断。
- 开源发票处理参考实现证明框架**完全可运行、已可采纳**，且六项设计原则得到验证（黑盒代理、分层纠正、配置驱动、人类治理、分级治理、领域无关）。

## 7. 优点

- **开源参考实现**：完整可运行、自包含、含测试套件，降低采纳门槛。

  - 调查代理的 LLM 规则发现依赖规则书质量，规则书不完整时可能有系统性的漏检偏差；
  - "保守偏差"（模糊视为合规）可能在某些高风险合规场景下不可接受。
- **应用限制**：
  - 要求 Acting Agent 必须输出 JSON 工件，对非 JSON 输出的智能体不适用；
  - 框架主要面向"规则治理型"业务流程（如文档处理、合规验证），对高度开放式任务的适用性不明；
  - 规则库随规模增长的管理负担是真实挑战，论文虽提出构想但缺少实证方案。
