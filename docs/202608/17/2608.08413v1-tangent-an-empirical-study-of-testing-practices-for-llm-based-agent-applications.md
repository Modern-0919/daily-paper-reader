## 摘要
基于大型语言模型（LLM）的智能体越来越多地被用于构建执行复杂、多步骤任务的应用，这些任务涉及推理、工具使用以及与外部环境的交互。尽管在基于LLM的智能体基准测试方面取得了快速进展，但很少有研究试图理解此类系统在实践中是如何进行测试的。特别是，智能体应用的测试级别、目标、数据模式、测试复杂性和验证策略仍未得到充分探索。在本文中，我们利用大量挖掘的开源项目语料库，对基于LLM的智能体应用中的测试实践进行了实证研究。我们构建了一个包含智能体应用、工具和测试的大规模数据集，并手动标注了来自240个模块的2,572个测试方法。通过这一分析，我们得出了一个涵盖测试夹具、数据、目标和断言的23种测试模式的分类体系，并按级别（单元、模块、集成）对测试进行了表征。我们还对10位构建智能体系统的高级行业从业者进行了结构化访谈作为补充。我们的结果表明，基于LLM的智能体应用的测试以范围狭窄的单元测试为主，对复杂交互、现实场景和非功能性需求的覆盖有限。测试通常依赖于简单的输入、大量的模拟和浅层的验证，且与智能体相关的测试表现出较低的结构复杂性。尽管行业实践比开源项目更重视非功能性测试，但两者都暴露出共同的不足，包括缺乏正式的测试基础、不明确的测试目标以及生成高质量测试数据的挑战。基于这些发现，我们提出了迈向更系统、更严格的智能体应用测试的研究方向，包括智能体可测试性的基础、形式化的测试目标以及基于故障的测试技术。

## Abstract
Agents built on large language models (LLMs) are increasingly used to build applications that perform complex, multi-step tasks involving reasoning, tool use, and interaction with external environments. Despite rapid progress in benchmarking LLM-based agents, very few studies have attempted to understand how such systems are tested in practice. In particular, testing levels, objectives, data patterns, test complexity, and validation strategies for agent applications remain underexplored. In this paper, we present an empirical study of testing practices in LLM-based agent applications using a large corpus of mined open-source projects. We construct a large-scale dataset of agent applications, tools, and tests, and manually label 2,572 test methods from 240 modules. From this analysis, we derive a taxonomy of 23 testing patterns across test fixtures, data, objectives, and assertions, and characterize tests by level (unit, module, integration). We complement this with structured interviews of 10 senior industry practitioners building agentic systems. Our results show that testing of LLM-based agent applications is dominated by narrowly scoped unit tests, with limited coverage of complex interactions, realistic scenarios, and non-functional requirements. Tests frequently rely on simplistic inputs, heavy mocking, and shallow validation, and agent-related tests exhibit low structural complexity. While industry practice places greater emphasis on non-functional testing than open-source projects, both reveal common gaps, including the lack of formal testing foundations, unclear test objectives, and challenges in generating high-quality test data. Based on these findings, we outline research directions toward more systematic and rigorous testing of agent applications, including foundations for agent testability, formalized test objectives, and fault-based testing techniques.

### 6.1 关键定量发现

| 发现编号 | 内容 | 定量证据 |
|----------|------|----------|
| Finding 1 | **测试以单元测试为主**，多数测试在隔离环境中验证单个工具或智能体；交互测试不足 | 61.8% 测试针对隔离的工具/agent；34.6% 针对交互行为；仅 3.5% 覆盖多工具调用；API 级测试仅 0.1% |

| Finding 5 | **推理行为几乎不被测试** | 仅 8.7% 测试断言推理相关行为；且多数仅检查“存在推理”而非“推理正确”；程序员不直接测试推理质量 |
| Finding 6 | **与外部环境交互测试极少** | 仅 4.08% 测试覆盖与非确定性非智能体组件的交互；2.4% 覆盖确定性组件交互；只 10.5% 覆盖多步骤场景 |

### 6.2 结构性复杂度发现

- 智能体相关测试中位 **NCLOC = 14**，圈复杂度中位数 = 1（即无分支的线性测试）；
- 即使计入夹具和辅助方法，中位数也仅上升至 NCLOC=20、圈复杂度=3；
- 每次测试中位断言数 = 2；构造函数调用中位数 = 1；库调用中位数 = 4；
- 结论：**智能体测试结构上非常简单，普遍缺少交互驱动和复杂场景验证**。

### 6.3 从业者访谈发现

- 测试策略：70% 做单元测试和集成测试、60% 做端到端测试，模块级（10%）和 API 级（20%）较少；
- 非功能测试：80% 提及安全、性能、可靠性、延迟、可扩展性等 NFR 问题（比开源项目更重视）；
- 监控与回归：50% 明确使用 OpenTelemetry 风格追踪，70% 提及可观测性，50% 在模型更新时做持续评估/回归测试；
- 主要挑战：**非确定性**（同一输入多次运行结果不一致）、**用户角色多样性**（persona 难以表征）、**测试充分性度量缺失**（一位受访者直言“No metrics at this point”）、**缺乏自动化测试生成**、**缺乏基础设施**；
- 未来预期：受访者认为自动化评估至关重要但尚不成熟，一位受访者指出“测试自动化完全缺失，用户每个项目都要从零开始”。

   - 仅覆盖 11 个主流框架，未涉及其他生态（如 AutoGen、CrewAI 等也未被选入最终数据集）；
   - 选择标准（Star ≥ 50、≥ 20 个测试模块）可能偏向成熟项目，无法代表小型或个人项目；
   - 仅 12 个项目的最终样本规模较小，难以推广到整个开源生态。
2. **访谈样本偏差**：10 位从业者全部来自 IBM 一家公司，可能反映特定企业文化和工作流，且样本量少，代表性有限。
3. **构造有效性风险**：
   - 智能体系统缺乏标准化的测试本体（ontology），论文自行定义的单元/模块/集成测试层级可能与其他研究存在不一致；
   - LLM 辅助的测试筛选（Gemini 标注）虽然采用宽松策略，仍可能产生假阴性或假阳性；
   - 端到端测试无法从仓库分析中确认（论文明确承认此限制）。
4. **分析深度局限**：论文对测试模式的分类虽细致，但没有做纵向（时间维度）分析——无法揭示测试实践随框架版本演化的动态过程；也没有分析测试在不同项目间的可移植性或复用情况。
5. **内部有效性风险**：框架与测试层级的关联可能是项目领域、规模等混淆变量的结果，论文虽用版本对比稍作缓解，但研究设计本质上是相关性而非因果性分析。
6. **未覆盖"测试后"环节**：论文聚焦于编码测试（encoded tests），对可观测性驱动的验证（observability-based validation）、生产环境监控等互补方法讨论有限，尽管从业者访谈部分有所涉及。
7. **无自动化和可操作工具产出**：论文提出了研究方向和路线图，但 **未开源可直接使用的测试生成或测试分析工具**（仅提供数据集和分析脚本），对实践的直接推动有限。

## 总结

> 该论文系统刻画了 LLM 智能体应用测试的现状：以窄范围单元测试为主、过度依赖 mock、测试数据简单、非功能测试匮乏、推理行为未经验证、结构复杂度低。行业实践比开源更重视 NFR，但两类来源都缺乏正式测试基础。论文建立了 23 种测试模式分类体系和公开数据集，提出了从测试理论、测试目标、故障测试、测试充分性到基础设施的研究路线图，为后续智能体测试研究奠定了实证基础。
