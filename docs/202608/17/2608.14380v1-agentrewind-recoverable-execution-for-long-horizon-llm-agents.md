## 摘要
许多现实世界任务要求LLM智能体在长时间的执行跨度内与环境交互。早期执行中出现的错误可能通过智能体上下文和环境状态传播，且其影响可能难以通过后续行动逆转。现有方法主要试图通过计划细化和安全检查来减少此类错误，但在错误发生后提供的支持甚少。为实现在长时程执行过程中的恢复，我们提出了AgentRewind，一个运行时恢复框架，记录智能体上下文和受控环境的对齐检查点，使智能体能够返回到较早状态，并利用先前尝试的信息继续执行。我们还构建了MettleBench，一个用于评估包含一系列相关需求的长时程工程任务中任务完成度和部分进展的基准。跨任务、多模型、执行策略和智能体框架的实验表明，AgentRewind在任务成功率和平均清单进展方面优于所比较的基线。

## Abstract
Many real-world tasks require LLM agents to interact with their environments over long execution horizons. Errors that occur early in execution may propagate through both the agent context and environment state, and their effects may be difficult to reverse through subsequent actions. Existing methods mainly seek to reduce such errors through plan refinement and safety checks but provide little support after errors occur. To enable recovery during long-horizon execution, we present AgentRewind, a runtime recovery framework that records aligned checkpoints of the agent context and controlled environment, allowing agents to return to an earlier state and resume execution with information from previous attempts. We also construct MettleBench, a benchmark for evaluating task completion and partial progress on long-horizon engineering assignments containing a series of related requirements. Experiments across tasks, multiple models, execution strategies, and agent harnesses show that AgentRewind improves task success rate and average checklist progress over the compared baselines.

### 1. 核心问题与整体含义（研究动机与背景）

- **研究动机**：长时程（long-horizon）LLM智能体在现实任务中需要在长时间跨度内与环境交互、调用工具并基于反馈调整行动。然而，执行早期出现的错误会沿着智能体上下文和环境状态双向传播，其负面影响难以通过后续追加的修正动作完全逆转——例如误删关键文件、破坏配置、污染数据库或形成错误的早期计划。
- **现有方法的不足**：
  - 现有研究主要聚焦于**计划细化**（如 ReAct、LATS）和**安全检查**（如 AgentDoG、GuardAgent），致力于在错误发生前降低错误概率或拦截风险行为；
  - 但即使单步错误概率很低，累积失败风险仍随轨迹长度增长；
  - 现有方法在**错误发生之后的恢复**方面支持甚少。已有自我反思类方法（Self-Refine、Reflexion、ExpeL）虽能利用先前尝试的信息改进后续行为，但无法在**同一轮执行中**从错误状态实质性回到更早阶段。
- **核心问题**：当长时程智能体在执行中陷入错误轨迹时，如何使其能够"回到过去"、在保留先前有效成果的基础上更换路径，从而完成原本难以完成的任务？
- **整体含义**：论文提出 **AgentRewind** 框架，将"运行时恢复（runtime recovery）"引入长时程智能体的执行循环，使智能体能够回退到早先的检查点并利用先前尝试的经验继续执行，从而显著提升长时程工程任务的成功率。

### 2. 论文提出的方法论

#### 2.1 核心思想

- 受软件工程中"断点/回滚"（checkpoint/rollback）思想的启发，将**智能体上下文（agent context）**与**受控环境状态（controlled environment state）**在每次LLM决策边界上**对齐记录**为可恢复检查点。
- 当智能体判定当前轨迹难以继续推进时，可选择某个历史检查点回退，并在恢复后的上下文中注入对失败尝试的**摘要记忆（rewind memory）**，在清除错误分支的同时保留失败的教训。

#### 2.2 关键技术细节

**（1）形式化定义**

- 标准前向执行过程：
  ```
  u_t ~ π(c_t),
  (s_{t+1}, o_{t+1}) = T(s_t, u_t),
  c_{t+1} = U(c_t, u_t, o_{t+1})
  ```
  其中 π 为LLM策略，T 为环境转移函数，U 为上下文更新函数，τ 为前向增长的轨迹。
- 可恢复检查点定义：`d_t = (c_t, s_t)`，即LLM决策边界的上下文与环境状态的对齐快照。
- 回退执行：选择检查点 d_k，恢复 `s'_k ← s_k`、`c'_k ← Inject(c_k, M)`，M为累积的rewind memory集合，然后从 `(c'_k, s'_k)` 产生新的后缀轨迹。

**（2）运行时恢复层（Runtime Recovery Layer）**

- 在智能体与受控环境之间作为**透明中间层**运行，仅挂钩两个点——LLM调用和工具调用；
- 正常执行时**透明记录**任务指令、LLM输入/输出、工具调用及结果、环境变化，不干扰原有交互；
- 通过**对齐记录**上下文与环境状态形成可恢复检查点，记录粒度为一个LLM节点与相邻工具节点。

**（3）重绕模块（Rewind Module）**

- 向智能体暴露两个控制工具：`backtrack_candidates`（列出候选回退目标），`backtrack_commit`（执行回退并携带记忆摘要）；
- 回退执行时：终止当前执行 → 从执行日志恢复保留的前缀（不重新生成或重跑）→ 恢复工作区文件系统到目标检查点 → 将累计的rewind memory作为系统消息注入恢复后的上下文；
- **恢复边界**：仅恢复工作区目录树的文件级状态；网络请求、外部服务调用等效果无法撤销，但保留的前缀不会触发二次副作用。

**（4）工作区快照与恢复**

- 工作区外维护一个bare git仓库，使用底层命令仅记录对象与提交，**不触碰工作树**；
- 每个节点前后各做一次工作区提交，LLM节点与其前的提交构成检查点 `d_t = (c_t, s_t)`；
- 恢复时比较当前树与目标树，删除目标不包含的路径并恢复其余文件；
- `.git` 目录默认跳过快照（工作区子目录中的 `.git` 会额外复制以支持历史重写类任务；工作区根目录 `.git` 不恢复）。

### 3. 实验设计

#### 3.1 基准数据集：MettleBench

- **构成**：82个任务，源自5个现有工程基准——Terminal-Bench 2.0、ProgramBench、SWE-bench、ProjectEval、GitTaskBench；
- **任务形式**：每个任务为一个包含**一序列有序、相互依赖的验收准则**（g₁,…,gₙ）的工程任务，共640个准则，每任务5–12个准则（均值7.80），准则类别包括数据完整性、正确性、证据保存、发布/打包、文件内容等；
- **评估指标**：
  - 任务成功率 Succ(s_T) = ∧ᵢ gᵢ(s_T)；
  - 清单前缀进度 ρ(s_T) = ℓ/n（ℓ为最长满足前缀长度）；
- **质量保证**：每个任务都有**前向唯一参考解**（线性脚本、无回滚、无重试，平均79.3行），保证任务无需恢复机制也可完成；评估器为纯Python确定性程序，无LLM参与评判；自动筛选分三关（参考解通过、乱序执行在依赖被移除处失败、初始工作区未解决）。

#### 3.2 对比方法

- **Continue**：验证反馈后从当前上下文与环境继续执行（标准前向执行基线）；
- **Restart with Experiences**：验证失败后重置环境到初始状态，携带前次失败经验重新尝试（类似Reflexion/ExpeL思想）；
- **Safety Review**：在Continue基础上，由AgentDoG安全审查模型拦截每个工具调用（代表安全检查路线）；
- **AgentRewind**：完整恢复框架。

#### 3.3 实验配置

- **基础模型**（7个）：GPT-5.4、GPT-5.4 mini、Qwen3.7-Max、Qwen3.5-27B、Kimi K2.5、DeepSeek-V4-Flash、GLM-5.1；
- **Agent框架**（3个）：mini-SWE-agent、FnCallAgent（Qwen-Agent）、CodeAgent（smolagents）；
- **主要实验**使用GPT-5.4 + mini-SWE-agent，条件统一：温度0.0（Kimi K2.5例外为0.6）、无步数/时间/超时限制、连续5次相同首个失败即终止；
- 每个配置独立运行3次。

### 6. 论文的主要结论与发现

- **MettleBench上基线差异显著**：Continue策略下7个模型成功率仅28.0%–73.2%，无模型饱和，验证了基准的区分度；更长轨迹不一定带来更好结果（GPT-5.4以最短平均轨迹取得第二好成绩）；
- **AgentRewind在所有设置下均优于最强基线**：
  - GPT-5.4：成功率87.8%（较Continue +25.6pp），清单进度94.3%（+12.9pp）；
  - GPT-5.4 mini：成功率51.2%（+17.5pp），清单进度73.5%（+8.9pp）；
  - 3个agent harness上都有一致的提升；
- **恢复增益随任务水平增长**：按Continue轨迹长度分三分位后，AgentRewind在中、长时程任务上的优势更大，说明回退机制在标准前向执行"卡住"时尤为有效；
- **跨基准验证**：在完整的Terminal-Bench 2.0上，AgentRewind达到83.1%成功率（Continue为78.7%），证明效果不限于MettleBench的任务形式；
- **恢复能力**：从50个相同的失败终点出发，AgentRewind的恢复率为30.0%（Continue仅8.0%），清单进度变化+12.2pp（Continue为+5.1pp）；
- **消融结果**：移除环境回退降幅最大（成功率降至43.9%），移除rewind memory（51.2%）、移除上下文回退（65.9%）均有明显退化——三者互补且缺一不可；
- **统计显著性**：12项Wilcoxon检验中11项在Holm校正后显著（唯一例外是GPT-5.4 mini任务成功率vs Restart，但进度指标显著）；
- **案例研究**展示了AgentRewind在Astropy FITS交接任务中的具体优势：保留已验证的库修复、恢复原始fixtures、清除错误分支，最终达到10/10清单进度，而Continue停在9/10、Restart历经26次尝试停在8/10。

### 7. 优点

- **问题定位准确且有价值**：精准切入长时程智能体"错误发生后难以恢复"这一真实痛点，与现有"预防优先"的路线形成互补；
- **方法设计优雅且实用**：将调试中的"回退到检查点"思想引入agent执行，**对齐恢复上下文与环境状态**、保留前缀、注入rewind memory的组合，逻辑自洽且工程实现完整（bare git、低层命令、BaseException传递回退信号等细节处理周详）；
- **基准构建严谨**：MettleBench采用有序、相互依赖的验收准则，并通过"前向无回滚参考解"保证任务可解性、通过纯确定性评估器保证公平性，具备人工审查和多维评分，方法论附录详细透明；
- **实验设计全面公正**：多种模型、多种框架、多种策略、跨基准验证，辅以配对恢复实验、组件消融和统计显著性检验，且如实报告可重复性数据；
- **有效性超出单一benchmark**：在Terminal-Bench 2.0上的验证增强了结论的普适性。

### 8. 不足与局限

- **恢复边界受限**：AgentRewind只能恢复**受控环境**（工作区文件系统），对外部副作用（网络请求、外部服务调用、外部运行时状态）无法撤销；虽然保留前缀不重放可避免再次触发，但已发生的外部效果依然存在；
- **依赖外部验证发现问题**：系统本身不主动检测"执行是否陷入困境"，而是依赖验证器反馈和智能体自行判断是否回退，缺乏内在的进度自我评估机制；
- **实验资源报告不透明**：未报告具体算力消耗、GPU配置和总计算成本，不利于其他研究者复现成本和实际部署的可行性评估；
- **可重复率有待提高**：74.7%的端到端判定一致性意味着仍有约1/4的任务在重复实验中结果不稳定，虽然论文承认这是上界且部分归因于智能体轨迹本身，但仍提示结果的稳健性有改进空间；
- **评估场景仍属特定类型**：任务覆盖以命令行为主的工程场景（Terminal-Bench、SWE-bench等），未覆盖更广泛的GUI操作、多Agent协作、多系统松耦合环境等长时程场景；
- **基准数据来自LLM生成并经过筛选**：虽然经过了确定性门控和人工审查，但验收准则和任务说明由LLM代理编写，可能引入一定偏差；
- **无法完全保证对最新模型的有效性**：随着基础模型能力提升，智能体可能需要更少的回退；恢复框架对未来模型的经验记忆整合方式（"rewind-aware models"）仍是未开发的开放方向。
