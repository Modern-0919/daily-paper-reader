## 摘要
移动智能体基准测试日益依赖基于LLM的评判员来评估任务完成情况，然而这些评判员在移动智能体轨迹上的可靠性在很大程度上仍未得到检验。我们引入了MobileJudgeBench，一个用于系统评估移动智能体轨迹上LLM-as-judge方法的基准测试。该基准测试包含931条人工标注的轨迹，涵盖6个移动智能体基准、4个智能体模型和68个应用。我们评估了6种评判方法（五种改编自SPA-Bench、A3的两种模式、AndroidArena和AgentRewardBench，外加我们设计的一个简单基线）在多个LLM后端上的表现。实验揭示了三个关键发现。第一，一个使用采样截图的简单基线评判员与专门构建的方法相比具有竞争力，且常常超越后者，这表明更复杂的评判流程并不能持续提高评判质量；在有竞争力的方法中，LLM主干是主要驱动力。第二，基准质量指标能可靠预测实际应用中的评判员效用：它们与用于评估的智能体排名保真度以及评判员作为策略内强化学习奖励信号时的下游性能均相关。第三，跨两个LLM后端的失败分析揭示了性质相反的失败模式，一个保守，一个宽松，这与后端模型的精确率-召回率特性相关。

## Abstract
Mobile agent benchmarks increasingly rely on LLM-based judges to evaluate task completion, yet the reliability of these judges on mobile agent trajectories remains largely unexamined. We introduce MobileJudgeBench, a benchmark for systematically evaluating LLM-as-judge methods on mobile agent trajectories. Our benchmark comprises 931 human-annotated trajectories spanning 6 mobile agent benchmarks, 4 agent models, and 68 apps. We evaluate 6 judge methods (five adapted from SPA-Bench, A3 with two modes, AndroidArena, and AgentRewardBench, plus a simple baseline we design) across multiple LLM backends. Our experiments reveal three key findings. First, a simple baseline judge with sampled screenshots is competitive with, and often exceeds, purpose-built methods, indicating that more elaborate judge pipelines do not consistently improve judge quality; among competitive methods, the LLM backbone is the primary driver. Second, benchmark quality metrics reliably predict real-world judge utility: they correlate with both agent ranking fidelity for evaluation and downstream performance when judges serve as reward signals for on-policy reinforcement learning. Third, failure analysis across two LLM backends uncovers qualitatively opposite failure profiles, one conservative and the other permissive, linked to the backbone's precision-recall characteristics.

## 一、核心问题与整体含义

- **研究动机**：移动智能体基准测试（如 AndroidWorld、SPA-Bench、A3、AndroidArena 等）越来越依赖 LLM 作为自动评判员（LLM-as-judge）来判断任务完成情况。然而，这些评判方法在移动智能体轨迹上的可靠性从未被系统检验。
- **关键风险**：
  - 不准确的评判员会产生有噪声的排行榜，即使 10–15% 的误判也可能显著改变智能体排名。
  - 当评判员被用作强化学习（RL）训练中的奖励信号时，奖励错误会直接破坏学习过程。
- **论文含义**：作者提出 **MobileJudgeBench**，据称是第一个在移动智能体轨迹上系统评估 LLM-as-judge 方法的基准，填补了“评判员本身需要被评估”的空白。

## 二、方法论

- **总体思路**：构建包含 931 条人工标注轨迹的基准库，设计统一评估流程，将任意评判方法映射为标准分类指标；并通过下游任务（智能体排名、RL 训练）验证基准指标的预测有效性。
- **数据构建细节**：
  - 轨迹来源：6 个移动智能体基准；4 个智能体模型（GPT-5-mini、Qwen2.5-VL-72B、UI-TARS-72B、Llama-3.3-70B）；289 个任务；68 个真实 Android 应用。

- **评估框架**：
  - 轨迹级指标：Accuracy、Precision、Recall、F1、Balanced Accuracy（“正类”定义为实现目标即成功）。

## 六、主要结论与发现

1. **简单基线足够强**：仅用均匀采样截图的 Simple Baseline 在多个后端（Qwen、GPT、Gemini）上取得最优（最高 90.9%），在其余后端也能与专门方法持平，更复杂的评判流程并不能持续带来收益。
2. **后端模型是决定性因素**：在有竞争力的方法中，方差分解显示 backbone 主导准确性差异（排除两个最弱的 A3 模式后，method 解释 11%、backbone 解释 49%）。
3. **指标可预测效用**：
   - 对“智能体评估”任务：F1（ρₛ=0.90）与 balanced accuracy（ρₛ=0.87）最强预测排名保真度；balanced accuracy 最好预测成功率估计误差（ρₛ=-0.79）。
   - Precision 对两个下游指标均无预测力，说明需要平衡分类而非单纯高精确率。
   - 对 RL 训练：评判准确率与训练后成功率的排序一致（规则检查器 > GPT-5-mini > GPT-5.2/Qwen），且在准确率相等时，高 precision 的 GPT-5.2 比高 recall 的 Qwen 训练效果略好（best-checkpoint 约定下 easy set 高 2.7pp）。
4. **失败模式相反**：
   - GPT-5-mini 后端的评判偏向“保守”：错误以假阴性为主（48 个 hard-core 中 30 FN），主因是 last-frame anchoring、unfamiliar success state。
   - Qwen2.5-VL 后端的评判偏向“宽松”：错误以假阳性为主（78 个 hard-core 中 71 FP），主因是 constraint violation、partial completion。
   - 两个后端共享的弱点是 surface UI match（表面视觉相似即判定成功）。

## 七、优点

- **填补空白**：首次针对移动智能体轨迹构建评判员基准，以人工标注为金标准，覆盖多基准多应用，具有高代表性。
- **方法论严谨**：统一轨迹格式与评估管线，明确分类指标定义；进一步以“下游任务（排名、RL 训练）验证基准指标”，形成闭环评估，超越单纯报准确率的做法。
- **设计克制**：提出可配置的 Simple Baseline，使消融分析能干净分离截图数量、分辨率、UI 元数据、推理等各因素的影响。
- **失败分析有洞见**：识别出后端的保守/宽松失败画像，并给出可操作的改进方向（如增加截图数量、主动验证）。
- **透明度高**：公开算力、超参、协议细节，并附有伦理考量、数据许可与标注流程说明。

## 八、不足与局限

- **任务定义窄**：仅评估二分类成功/失败，丢弃了最优性、效率、部分进度等维度（作者在 Limitations 中承认，并辩称二分类是当前基准与 RL 管线实际使用的信号）。
- **训练实验覆盖有限**：
  - 仅 AndroidWorld 环境；评判方法只用了 Simple Baseline，未比较其他 5 种方法作为奖励信号。
  - 训练集仅用 easy task 子集；与完整任务套件上的表现存在 best-checkpoint vs. 固定 checkpoint 的差异，结论强度有限。
- **潜在偏差风险**：
  - 标注员来自单一机构、9 人规模，跨文化/跨语言泛化未知。
  - 失败分类（7 类根因）带有主观性，尽管双人编码 κ 很高，但只能证明分类可重复性，不保证绝对正确性。
  - 存在“利用评判弱点刷榜”的伦理风险，作者认为透明度收益大于风险。
- **成本与可复现性**：部分后端通过 OpenRouter API（第三方），版本锁定与 API 非确定性虽做了敏感性分析，但无法完全消除；费用未统计。
- **限于移动域**：结论不一定直接迁移到 web/desktop agent 与更广义的 GUI agent。
