## 摘要
检索能够识别可能重要的过往轨迹，但它并未说明在用户、实体、约束或环境状态发生变化后，行动智能体应如何使用该轨迹。我们将检索后复用这一步识别为长时程轨迹记忆的一个独特瓶颈，并构建了一个评估框架，该框架固定候选检索、目标状态、模型、解码和工具预算，同时改变提供给智能体的支持。我们以查询条件复用（QCR）实例化该框架，这是一种刻意简单的目标绑定笔记，记录了可复用程序、恢复绑定、适用条件和验证要求。QCR旨在检验复用假设，而非宣称一种普遍偏好的记忆格式。在WebArena、WorkArena和AppWorld的2,391个目标实例中，QCR达到了62.3%的平均成功率，比完整轨迹高出10.7个百分点，同时在线令牌使用减少48.9%。摘要重排序为94.8%的目标选择了可复用记忆，使最终任务成功率与预言式可复用选择器相差1.8个百分点以内。按轨迹长度和源-目标绑定转移的分析显示，随着轨迹变长或源特定值发生变化，直接轨迹注入失去了大部分效用，而目标绑定支持保留了更大份额的测量增益。由此产生的框架将检索质量与将检索到的经验转化为安全、有用的新任务支持这一问题的分离开来。

## Abstract
Retrieval can identify a past trajectory that may matter, yet it does not specify how an acting agent should use that trajectory after users, entities, constraints, or environment state have changed. We identify this post-retrieval reuse step as a distinct bottleneck for long-horizon trajectory memory and formulate an evaluation framework that holds candidate retrieval, target state, model, decoding, and tool budget fixed while varying the support delivered to the agent. We instantiate the framework with query-conditioned reuse (QCR), a deliberately simple target-bound note that records a reusable procedure, bindings to recover, applicability conditions, and verification requirements. QCR serves to test the reuse hypothesis rather than to claim a universally preferred memory format. Across 2,391 target instances in WebArena, WorkArena, and AppWorld, QCR reaches 62.3% average Success, 10.7 points above Full Trajectory, while using 48.9% fewer online tokens. Summary reranking selects a reusable memory for 94.8% of targets, placing end-task Success within 1.8 points of an oracle reusable selector. Analyses by trajectory length and source--target binding shift show that direct trajectory injection loses much of its utility as traces grow longer or source-specific values change, whereas target-bound support preserves a larger share of the measured gain. The resulting framework separates retrieval quality from the problem of turning retrieved experience into safe, useful support for a new task.

## 1. 核心问题与研究动机

- 现有智能体记忆研究大多聚焦于“存取”与“检索”：能否存下、能否召回、能否回答关于历史交互的问题。但论文指出，对**长时程任务轨迹（long-horizon trajectories）** 而言，检索到一段历史经验后，**“如何复用”** 才是真正的瓶颈。
- 长轨迹与短事实不同：短事实被检索到后，通常直接包含了答案或指令；而长轨迹虽包含可迁移的工作流，但其中的用户、实体、路径、日期、环境状态等**绑定值（bindings）** 往往已经失效。直接把原始轨迹扔给智能体，可能造成“进入正确的子系统，却使用了过期的参数或对象”。
- 论文将这一现象概括为 **“瓶颈随记忆长度右移”**：从短事实到长轨迹，记忆可以携带更多可复用信息，但主要困难从“检索”转移到“检索后的复用、重绑定与执行”。
- 因此，论文的核心主张是：记忆系统评估不应止于检索命中率，而应衡量“历史经验是否能真正提升当前任务的成功率与效率”。

## 2. 方法论

### 2.1 核心思想

- 提出 **查询条件复用（Query-Conditioned Reuse, QCR）**：在检索之后加入一个“目标条件化支持生成”环节，将选中的历史轨迹转换为**目标绑定（target-bound）** 的紧凑支持笔记，而不是把原始轨迹直接注入。
- QCR 并非提出一种通用记忆格式，而是作为一种“诊断性干预”，用来检验“复用环节”是否是独立于检索环节的真正瓶颈。

### 2.2 QCR 支持笔记的四字段结构

1. **工作流不变式（workflow invariant）**：保留仍适用于目标任务的行动顺序、决策规则和验证步骤。
2. **需重新获取的绑定（bindings to re-obtain）**：显式指出哪些值（如实体、用户、记录 ID、路径、日期、参数）必须从目标侧重新获取，禁止照搬源轨迹中的值。
3. **适用条件（applicability conditions）**：说明源轨迹生效的前提条件；若目标状态不满足，应拒绝复用。
4. **验证护栏（verification guardrail）**：要求智能体在提交最终结果前，对目标侧结果进行验证。

### 2.3 评估框架

- 构建一个**统一冻结记忆库**：包含来自 WebArena、WorkArena、AppWorld 的 623 条已验证成功轨迹，跨环境混合存储。
- 对每个目标任务，固定检索器返回相同的 top-5 候选集合；再通过一个轻量级重排序器从中选择一条轨迹，所有记忆条件共享该选中记录。
- 四种条件仅改变“同一选中经验”的表示与使用方式：
  - **No Memory**：无历史记忆；
  - **Generic Summary**：源轨迹的独立摘要（目标到达前生成）；
  - **Full Trajectory**：直接注入原始完整轨迹；
  - **QCR**：目标条件下的四字段支持笔记。
- 对比时严格固定：候选检索集合、目标状态、模型、解码配置、工具预算、验证器。
- 评测指标：端到端成功（Success）、里程碑完成（Milestone）、API 调用次数、非重叠在线 token 数。在线 token 的计算包括基础 prompt、注入记忆、支持生成输入输出和行动输出。

## 3. 实验设计

### 3.1 数据集 / 场景

- **WebArena**：网页交互任务；
- **WorkArena**：知识工作类网页任务；
- **AppWorld**：API/应用交互任务。

### 3.2 Benchmark 与任务构建

- 从 623 条成功后源轨迹出发，通过 **binding-aware rewrite** 构造目标任务：保持源任务工作流不变，但改变一个或多个目标特定绑定值。共生成 **2,391 个目标实例**，平均每个源轨迹对应 3.84 个目标变体。
- 绑定转移分为四档：无改写、小改写、中改写、大改写。
- 轨迹长度分组：Short（5–10 动作）、Medium（11–20）、Long（21–35）、Very Long（>35）。
- 检索使用 BGE-M3 嵌入检索器；排序器、支持生成器与执行智能体均为 DeepSeek-V4-Pro。

### 3.3 对比方法

- **No Memory**：无历史记忆基线；
- **Generic Summary**：仅从源轨迹生成的通用摘要；
- **Full Trajectory**：完整历史轨迹直接注入；
- **QCR**：本文提出的查询条件复用支持笔记；
- 另外还对比了：随机 top-5 选择、检索器 top-1 直选、摘要重排序选择、Oracle 可复用选择。

### 实验规模

- 共 2,391 个目标实例；每个条件每个目标运行 3 个随机种子，结果取平均。
- 三个环境、四个记忆条件、多种分层分析（轨迹长度、绑定转移、选择机制）以及检索与重排序诊断，实验数量较为充足。

### 充分性与公平性

- 控制变量较严格：同一目标的正取候选集、选中轨迹、模型、解码、工具预算、验证器全部固定，差异仅来自记忆的表示与使用方式。
- 盲注标注（Cohen’s κ = 0.87）用于判定候选轨迹是否为可复用工作流，避免仅靠最终成功来推断。
- 在线 token 计算避免了 API 输入重复计数，成本报告较细致。
- 局限：只覆盖“成功源轨迹 + 单条选中记忆 + 受控绑定改写”，未覆盖自然重复出现的任务历史、部分失败轨迹、多记忆组合、开放式记忆获取；因此实验充分但不全面。

## 6. 主要结论与发现

- **QCR 显著优于直接轨迹注入**：平均 Success 达 62.3%，比 Full Trajectory 高 10.7 个百分点；在线 token 为 9.4k，比 Full Trajectory 的 18.4k 减少 48.9%，API 调用也最少。
- **三个环境上结论一致**：QCR 在 WebArena、WorkArena、AppWorld 的成功率和里程碑均最高；相对 No Memory 的提升分别为 23.2、23.8、24.7 个百分点。
- **检索与复用可以解耦**：top-5 候选覆盖率高（配对轨迹 95.6%、可复用轨迹 97.8%），但 top-1 直取只有 78.9% 配对准确率；摘要重排序最终达到 91.7% 配对准确率、94.8% 可复用记忆准确率，且端到端 Success 与 Oracle 可复用选择仅差 1.8 个百分点。
- **轨迹越长，直接注入的效用越弱**：Full Trajectory 的效用从 Short 组的 +18.4 点降至 Very Long 组的 +2.9 点，保留率仅 15.8%；QCR 在 Very Long 组仍保持 +13.2 点，保留 60.3% 的短轨迹效用。
- **绑定变化越大，直接注入越容易携带过期值**：在大改写下，Full Trajectory 的效用仅 +2.2 点，且 46.9% 的目标出现陈旧绑定错误；QCR 仍有 +20.1 点，陈旧绑定错误率降至 10.9%，正确重绑定率从 31.7% 提升到 77.8%。

## 7. 优点

- **清晰的问题切分**：首次系统性地把“检索质量”与“检索后复用”分开评测，给出可直接复用的评估协议。
- **控制严格的实验边界**：固定候选集、选中记录、模型、解码和工具预算，使差异可归因于记忆的表示与使用方式。
- **统一的跨环境记忆池**：不分环境建档，允许跨环境迁移，比单环境评测更接近真实部署。
- **绑定感知的目标构造**：从源轨迹出发构造不同“绑定转移程度”的目标，直接针对长轨迹复用的核心难点。
- **低成本、可解释的 QCR 设计**：四字段笔记简单透明，便于诊断“复用”是否独立于“存储”和“检索”。
- **审计完整性**：提供 per-run 审计账本、token 分解、标注规则与信息边界说明，提升可复现性。

## 8. 不足与局限

- **覆盖范围有限**：仅研究成功源轨迹和单条记忆选择，未涉及多条轨迹组合、自然重复任务、部分失败经验或开放式记忆积累。
- **绑定改写由人构造**：源-目标关系由受控改写生成，可能无法完全代表真实世界中任务变化的分布与自然性。
- **长度分组与难度混杂**：作者也承认，不同长度组的 No-Memory 成功率差异很大，因此长度对效用下降的结论是“关联”而非严格的因果估计。
- **未建模安全与副作用**：评测只看已验证成功，未衡量不可逆副作用、策略违规或复用轨迹带来的潜在风险。
- **未单独隔离 QCR 各字段的贡献**：框架层面验证了“目标条件化支持”整体的价值，但未证明四个字段各自独立有效的程度。
- **模型与时间成本未报告**：未提供训练/推理基础设施细节，依赖单一闭源 API（DeepSeek-V4-Pro），跨模型泛化性未知。
