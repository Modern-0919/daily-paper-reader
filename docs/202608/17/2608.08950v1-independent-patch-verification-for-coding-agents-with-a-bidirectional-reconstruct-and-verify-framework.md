## 摘要
由大语言模型驱动的自主编码代理现在可以直接根据错误报告生成代码补丁，但一个根本性差距依然存在：一旦生成补丁，就没有机制独立验证它是否真正解决了所报告的问题。先前的工作试图通过迭代自我改进和推理时扩展来解决这一问题，但这些方法要么在产生补丁的相同解释下审查补丁，要么扩大候选生成范围而不验证单个补丁，并且都没有为评估补丁正确性提供明确的验证信号。我们提出RETRACE，一种无需训练的后生成验证框架，通过双向重建与协调得到这样的信号。当编码代理针对某个问题生成候选补丁时，RETRACE执行前向重建，从问题和代理的轨迹中构建明确的修复理由；然后，后向重建仅从补丁及其轨迹（不访问原始问题）独立推断补丁似乎要解决的问题描述，并将此重建与原始问题进行比较以产生一致性判定；随后，协调阶段检查前向理由与补丁之间的一致性，诊断任何不一致的根源，并提出补丁提交或针对性的修订指导。在SWE-bench Verified上使用两个主干模型（GPT-5-mini和MiniMax-2.5）进行评估，RETRACE在mini-SWE-agent脚手架上将Pass@1分别提升了7.0%和3.6%，并在未修改的OpenHands上取得了相当的改进。消融实验表明，前向和后向阶段都对整体改进有贡献，而增加协调阶段则带来进一步收益。

## Abstract
Autonomous coding agents powered by large language models can now generate code patches directly from bug reports, but a fundamental gap remains: once a patch is produced, no mechanism independently verifies whether it truly resolves the reported problem. Prior work has sought to address this through iterative self-refinement and inference-time scaling, but these approaches either review the patch under the same interpretation that produced it or broaden candidate generation without verifying individual patches, and neither provides an explicit verification signal for assessing patch correctness. We propose RETRACE, a training-free post-generation verification framework that derives such a signal through bidirectional reconstruction and reconciliation. When a coding agent generates a candidate patch for an issue, RETRACE performs forward reconstruction to build an explicit repair rationale from the issue and the agent's trajectory; backward reconstruction then independently infers, from the patch and its trajectory alone and without access to the original issue, a description of the problem the patch appears to address, and compares this reconstruction against the original issue to produce an alignment verdict; a reconciliation stage then checks the consistency between the forward rationale and the patch, diagnoses the source of any misalignment, and either submits the patch or produces targeted revision guidance. Evaluated on SWE-bench Verified with two backbones (GPT-5-mini and MiniMax-2.5), RETRACE lifts Pass@1 by 7.0% and 3.6% respectively on the mini-SWE-agent scaffold, and delivers comparable gains on OpenHands without modification. Ablation experiments show that both the forward and backward stages contribute to the overall improvement and that adding reconciliation yields further gains.

- **推理时扩展（Inference-time Scaling）**：如 CodeMonkeys、Satori-SWE 等，通过重复采样和搜索扩大候选补丁的覆盖面，但仍然缺少评估**单个补丁**是否与报告问题一致的信号，且依赖测试用例作为筛选器，在缺乏可靠测试预言时无法工作。

**核心洞察**：论文借鉴数学验证思想——从推导出的答案反向推理以恢复原始条件并检验二者一致性，提出了 **RETRACE** 这一无需训练的训练后（post-generation）验证框架，通过**双向重建与协调**，为补丁正确性提供显式的、独立的验证信号。

## 2. 论文提出的方法论：核心思想、关键技术细节、流程

### 核心思想
当编码代理针对某问题 I 生成候选补丁 p 后，RETRACE 将 p 视为"待验证的提议"而非"正确解"，在不依赖测试执行和参考答案的前提下，通过三阶段流水线产生验证信号并给出有针对性的修订指导。

### 三大核心阶段

#### 阶段一：前向重建——构建修复理由（Forward Reconstruction of Repair Reasoning）
- 输入：原始问题 I 和前向轨迹视图 τf（包含仓库探索、观察和中间推理，但不包含候选补丁）
- 输出：修复理由 ϕ = F(I, τf) = ⟨E, r, s⟩
  - **E（证据恢复）**：从轨迹中提取直接支撑最终决策的仓库证据，剔除探索性弯路中的观察；
  - **r（推理链重建）**：将分布式决策重构为从问题到修复的逻辑连贯推理链，要求每步有证据或前序步骤支撑；
  - **s（预期修复）**：描述预期变更的行为、位置和范围，不假设其正确性。
- 关键设计：补丁对前向路径不可见，防止事后用实现弥补推理缺口。

#### 阶段二：后向重建——重建被解决的问题（Backward Reconstruction of the Addressed Problem）
- 输入：候选补丁 p 和后向轨迹视图 τb（包含解释实现所需的仓库上下文，但**不含原始问题 I**）
- 输出：重建的问题描述 Î = B(p, τb)
- 内部步骤：先进行**补丁解释**（识别补丁功能的语义含义，而非逐行概括 diff），再结合轨迹进行**轨迹语境化解释**（用轨迹消解补丁歧义；当轨迹意图与补丁冲突时以补丁实际实现为准），最终组合成**问题重建**（描述受影响行为、触发条件、变更前后行为、影响范围和实现意图）。
- 关键设计：扣留原始问题，确保重建独立于生成补丁时的解释。

#### 阶段三：协调——前向-后向一致性检查与修订决策（Forward–Backward Reconciliation）
- **问题对齐**：比较重建问题 Î 与原始问题 I，产生一致性判定 v ∈ {Same, Partial, Different} 和分歧记录 d（包括一致项、遗漏项、冲突项）；比较基于语义而非表面文本相似度。
- **补丁-推理一致性**：检查补丁 p 是否实现了前向理由中的预期修复 s，是否保持推理链中的行为与范围，是否引入了证据不支持的多余改动。
- **修订诊断**：区分两类不一致来源——
  - 实现不一致（patch 未完全实现意图）vs. 推理不一致（推理链本身证据不足或断裂），或两者兼有。
- **协调决策**：输出决策 a ∈ {Submit, Revise-Patch, Revisit-Reasoning, Revise-Both} 和有序修订计划 s′；修订计划指明应重新审视的代码位置/修复组件、偏差动机和目标行为效果。
- **执行循环**：验证意见附加到代理工作上下文中，代理沿用原有工具和编辑机制进行修订；修订完成后重跑后向重建与协调，直到 Submit 或修订预算耗尽；仅当决策为 Revisit-Reasoning 时才重跑前向重建。

### 形式化表示
- 候选补丁生成后：ϕ = F(I, τf)；Î = B(p, τb)；(v, d) = A(I, Î)；(a, s′) = R(I, ϕ, p, Î, v, d)

## 6. 论文的主要结论与发现

1. **RETRACE 显著提升补丁解析率**：在 SWE-bench Verified 上，GPT-5-mini 提升 7.0%、MiniMax M2.5 提升 3.6%，且在不同后端模型上表现一致。
2. **框架是脚手架无关的**：无需修改即可在 OpenHands 上获得相当幅度的提升（+19.2% 和 +7.5%）。
3. **前向与后向路径解决互补的失败模式**：前向重建通过重构上下文纠正错误的编辑决策；后向重建则捕获补丁效果偏离报告问题的情形；两者组合（完整 RETRACE）能解决任一单一路径都无法解决的问题。
4. **收益来源是验证信号而非额外计算**：Self-Refine 在相同推理预算下未改善甚至降低了性能，而 RETRACE 的提升源于独立的双向重建和协调机制。
5. **成本可控**：通过输入共享和提示缓存，双向验证可以实现与基线持平甚至更低的 API 成本。
6. **无需训练数据与测试执行**：RETRACE 不依赖执行信号或 ground-truth 补丁，可在测试预言不可用时工作。

1. **独立验证信号的新颖设计**：通过"扣留原始问题"来强制后向重建的独立性，类比数学中反向推导验证，概念清晰且直觉有力，能为每个单个补丁提供显式的正确性信号。

2. **修订预算与收敛性分析不足**：框架依赖迭代修订直到 Submit 或预算耗尽，但论文未分析迭代轮数分布、每轮修订的成功率、以及不同预算设置对最终 Pass@1 的影响。没有展示从 Revise-Patch 到 Submit 的平均循环次数，也没有讨论是否存在陷入循环或反复修改后性能下降的情况。

3. **对主干模型质量的依赖**：RETRACE 的三个阶段全部依赖 LLM 的推理能力，包括重建理由、重建问题、语义对齐和协调诊断。如果主干模型本身较弱，这些推理步骤可能产生噪声，甚至误导修订决策。论文只测试了 GPT-5-mini 和 MiniMax M2.5，两者均为较强模型，未探索小模型或更弱模型下框架的鲁棒性。

4. **协调阶段的自动化评估不透明**：论文对"问题对齐"（Same/Partial/Different）和"修订诊断"（推理不一致 vs 实现不一致）的评判标准描述较为抽象，未提供具体的提示词示例或人工评估的准确率，读者难以复现其判定逻辑。对齐判断是否完全由 LLM 自动完成、是否需要人工介入，也未明确说明。

5. **隐藏假设：前向轨迹的质量**：阶段一依赖代理的探索轨迹 τf 来重建推理链。如果代理初始探索本身路径混乱、信息冗余或缺失关键证据，重建出的"修复理由"也可能失真。论文未分析前向轨迹质量对验证效果的影响，也未设计针对轨迹质量低时的兜底机制。

6. **补丁与实现一致性的判定粒度**：阶段三检查补丁是否实现预期修复时，仅依靠推理链和证据，但缺少对代码语义层面的静态或动态校验。对于补丁中存在的细微逻辑错误（如边界条件、竞态条件），仅靠文本推理难以捕捉，这可能限制了验证信号在更深层 bug 上的判别力。

7. **未报告失败案例分析**：论文虽展示了整体的提升幅度，但没有深入剖析 RETRACE 依然失败的实例（例如协调错误地将 Same 判为 Different，或错误修订导致原本正确的补丁被改坏）。失败模式的分析有助于理解方法的边界，但论文对此着墨较少。

8. **可能的评估偏差**：消融实验和 OpenHands 泛化实验均基于随机抽取的 120 问题子集，但该子集是否与完整 500 集分布一致（如难度、仓库大小）未做统计检验；且每个配置仅运行一次，即便使用贪婪解码，仍存在单次运行偶然性的可能。

## 9. 改进方向与未来工作

- **引入多轮验证与历史记忆**：在迭代修订中维护一份"已尝试的修复路径"记录，避免重复提出相同错误假设，并让协调阶段能跨轮次学习先前的失败诊断。
- **结合轻量级动态信号**：在无条件依赖测试执行的前提下，可选择性引入类型检查、静态分析或合约检查等廉价信号，增强协调阶段对实现一致性的判断。
- **更细致的对齐判定**：将 Same/Partial/Different 扩展为更细粒度的维度（如触发条件匹配、行为变更匹配、范围匹配），并输出结构化对齐报告，便于代理精准定位偏差。
- **验证信号的概率化表达**：让协调阶段输出置信度或概率分布（如"0.8 概率为 Same"），允许代理在不确定时主动请求人类澄清或采取保守策略。
- **扩展到多补丁生成场景**：当前框架验证单个补丁，未来可与推理时扩展方法结合，对每个采样补丁进行验证并选择协调分数最高的候选，形成"生成-验证-选择"闭环。

## 10. 总结性评价

RETRACE 提出了一种极具启发性的训练后验证框架，将数学中"反向推导验证答案"的思想映射到代码补丁正确性验证上，通过扣留原始问题强制后向重建的独立性，从根本上区别于依赖同一解释的自我精炼方法。实验设计严谨，控制了推理预算、验证了组件贡献和跨脚手架泛化性，且成本分析考虑了实际部署中的缓存经济性。虽然论文在评估范围、鲁棒性和诊断透明度上仍有可探讨之处，但该方法为编码代理的可靠性提升提供了一个无需训练、无需测试预言、可直接嵌入现有工作流的实用范式，是该领域一个有价值的贡献。
