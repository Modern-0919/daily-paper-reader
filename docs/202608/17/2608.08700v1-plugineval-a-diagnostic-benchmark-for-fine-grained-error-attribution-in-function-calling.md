## 摘要
随着大型语言模型日益作为自主代理运行，工具路由的可靠评估变得至关重要。当前基准存在三个结构性局限：遵循幂律分布的数据使稀有场景代表性不足；缺乏对抗性硬负例使得模型间的性能差异不明显；标注流程依赖于未经执行验证的LLM判断。在本文中，我们介绍了PluginEval，一个通过两阶段框架构建的基准，系统地缓解了这些局限。首先，我们将工具路由表述为三个决策的序列，并将生成与验证分离。LLM提出候选调用，而确定性验证和真实API执行为其提供可靠的质量信号。其次，我们按能力、意图和边界对每个插件进行分解，以识别触发和排除场景。然后我们生成不同难度级别的查询以填补覆盖空白，包括针对三种失败模式的对抗性负例，并将其返回给第一阶段进行标注。这个过程形成了一个闭环，迭代直至覆盖收敛。在评估方面，我们超越了总体准确率。以金标准标注为依据的LLM评判器将失败分类为漏调用、虚假调用或参数错误，为每个模型生成详细的错误概况。我们评估了五个模型系列，包括专有模型和开放权重模型，分析了它们在不同难度级别和错误类别下的表现，并通过与人工标注的一致性验证了评判器。

## Abstract
Reliable evaluation of tool routing is critical as Large Language Models increasingly operate as autonomous agents. Current benchmarks face three structural limitations: data distributions that follow a power law leave rare scenarios underrepresented; the absence of adversarial hard negatives obscures performance differences across models; and annotation pipelines depend on LLM judgments that have not been validated through execution. In this paper, we introduce PluginEval, a benchmark constructed through a two-stage framework that systematically mitigates these limitations. First, we formulate tool routing as a sequence of three decisions and separate generation from verification. LLMs propose candidate calls, while deterministic validation and real API execution provide reliable quality signals. Second, we decompose each plugin by capability, intent, and boundary to identify trigger and exclusion scenarios. We then generate queries at different difficulty levels to fill coverage gaps, including adversarial negatives targeting three failure modes, and return them to the first stage for annotation. This process creates a closed loop that iterates until coverage converges. For evaluation, we move beyond aggregate accuracy. An LLM judge anchored to gold annotations classifies failures as missed calls, spurious calls, or parameter errors, producing a detailed error profile for each model. We evaluate five model families, including proprietary models and models with open weights, analyze their performance across difficulty levels and error categories, and validate the judge through agreement with human annotations.

### 1. 论文的核心问题与整体含义

- **研究背景**：LLM 作为自主代理时，需要可靠的工具路由（tool routing）能力——即决定是否调用工具、选择哪一个插件、以及如何构造合法调用。现有基准无法充分衡量这一能力。
- **三个结构性局限**：
  - **数据分布幂律**：常见场景占比过高，稀有场景（如边界条件、排除场景）代表性不足，导致基准对模型弱点的诊断能力有限。
  - **缺乏对抗性硬负例**：缺少设计良好的对抗样本，模型间性能差异被压缩，难以区分真实能力差距。
  - **标注可靠性不足**：现有标注流程依赖未经执行验证的 LLM 判断，可能将语义错误标注为正确，或将合理调用标注为错误。
- **整体含义**：论文主张工具路由评估应超越聚合准确率，需要能够区分“漏调用、参数错误、虚假调用”等不同失败模式的细粒度诊断框架，并强调标注必须经过执行验证。

### 2. 论文提出的方法论

#### 2.1 工具路由的三级决策形式化

将工具路由建模为三级决策层次：

- f₁(q)：判断查询是否需要工具（必要性）
- f₂(q, t, d_t)：判断目标插件是否支持所需能力（相关性）
- f₃(q, t, d_t, S_t)：基于查询构造合法调用，若信息不足则返回 ⊥（可行性/参数落地）

每个查询-插件对标注为 y = (ℓ₁, ℓ₂, θ*)，标签空间包括：不必要工具调用、不相关插件、相关但信息不充分、合法调用。

#### 2.2 两阶段闭环构建框架（PCCF）

- **阶段一：执行落地的集成标注（Stage I: Execution-Grounded Ensemble Annotation）**
  - M 个生成器独立提出完整调用，经过确定性 schema 验证、参数评估器（S_arg）、真实 API 执行（MCP）、结果评估器（S_out）的层级验证。
  - 最终得分：s = λ_arg · S_arg + λ_out · S_out。
  - 拒绝的样本及其失败痕迹被保留并作为修复信号输入下一轮生成，进行迭代精炼（最多 R_max 轮）。
  - 关键设计：**生成与验证分离**——LLM 只负责提出候选，不参与自我验证。

- **阶段二：场景驱动的合成与行为校准（Stage II: Scenario-Grounded Synthesis and Behavioral Calibration）**
  - 对每个插件按“能力、意图、边界”分解为触发场景和排除场景。
  - 覆盖缺口定义为 Δ_r(u) = max{0, b(u) − n_r(u)}，仅对缺口为正的单元合成数据。
  - 难度校准：正例按推理深度分为 Easy/Medium/Hard；负例用冻结参考路由器在 K 次受控运行中计算行为难度 d_beh(x)。
  - 针对性负例分三类：Type A（域距离）、Type B（表面相似）、Type C（能力边界证据）。
  - 闭环终止条件：所有覆盖预算完成，或连续 L 轮覆盖提升低于阈值，或合成预算耗尽。

#### 2.3 金标准锚定的评估框架

- **语义一致性判据**：仅当预测调用的参数与金标准参数在用户查询语义下等效时才算正确，不允许仅凭“看起来合理”判定正确。
- **三级层次化验证**：
  1. 工具对齐（按工具名精确匹配）
  2. 参数过滤（排除空参数）
  3. 语义验证（LLM 判断语义等价性，返回 r ∈ {0,1} + 理由）
- **查询级错误归因**：每个失败查询被归入互斥类别——漏调用（miss recall）、参数错误（parameter errors）、虚假调用（over recall）；参数错误进一步细分为时间错误、缺失参数、值错误。正查询必须全部工具正确才计为成功。

### 6. 论文的主要结论与发现

1. **聚合分数掩盖失败模式差异**：GPT-5.4 参数错误率最低但漏调用率最高（33.72%），Claude Opus 4.6 漏调用率最低（13.95%）但虚假调用率偏高，Gemini 3.1 Pro 虚假调用率最低（18.55%）。相同分数可能来自完全不同的错误来源。
2. **难度组成高度影响评估结论**：将 Easy 比例从 0.40 提升至 0.60 后，所有模型 Recall 提升 14.7–21.2 个百分点。这意味着不控制难度分布的基准评测结论不可直接比较。
3. **时间错误是跨模型的共同弱点**：所有模型的时间错误率（7.96–10.41%）一致高于缺失参数和值错误，说明时间语义理解是工具调用的系统性瓶颈。
4. **模型排名在不同基准间漂移**：Claude Opus 4.6 在 PluginEval 和 BFCL 上第一，而 Gemini 3.1 Pro 在 APIBench 和 NexusRaven 上最优。DeepSeek V4 Pro 在 PluginEval 上超过 GPT-5.4 但在另外两个基准上落后。
5. **PCCF 组件的必要性**：移除内容验证使假阳性率从 0% 升至 78%；关闭迭代校准使累计通过率从 39.7% 降至 11.1%；闭环合成相对单次生成显著提升场景覆盖（3.88× vs 1.38×）并降低难度偏差（0.40 vs 1.16）。
6. **人类审计确认可靠性**：参考标注总体有效性 96.7%；评判器归因与人类一致性 94.3–97.0%，所有漏调用和虚假调用判定均获人类确认。

### 7. 优点

- **方法层面**：
  - 将“生成”与“验证”分离，避免 LLM 自评偏差，且失败痕迹用于迭代修复，形成可持续的标注质量改进闭环。
  - 将工具路由分解为三级决策，错误定位粒度清晰，能从“漏调用 vs. 参数错误 vs. 虚假调用”中判别模型短板。
  - 覆盖驱动合成与行为驱动校准结合，保证基准既覆盖长尾场景又区分模型能力。
  - 金标准锚定评判器设计严谨：工具对齐→参数过滤→语义验证的真正分层流程，避免工具选择错误与参数错误混淆。
- **评估层面**：
  - 人类审计覆盖了数据标注和评判器两层，验证链条完整，可信度高。
  - 跨基准对比揭示模型排序漂移，证明了 PluginEval 与其他基准的互补性。
  - 消融实验系统、有显著性检验，支持结论的可信性。
  - 查询级严格判分（部分完成不算成功）符合真实代理场景，避免了过于宽松的评分。

### 8. 不足与局限

- **实验设计层面**：
  - 单一评判模型（GPT-5.2），未测试评判器自身偏差或更换评判器后的结论稳定性。

  - 真实 API 执行依赖 MCP 环境，无法验证本次评估之外（如非 MCP 接口）的适用性。
- **未报告信息**：
  - 未报告算力/资源消耗，也缺少构建 PluginEval 的具体耗时和成本。
  - 未提供判断条件细节（如评估器 prompt 的敏感度分析），其他研究者难以精确复现。
- **潜在偏差风险**：
  - LLM 评估器在参数错误判定上仍存在约 7–12% 与人类不一致的情况，此类边缘案例的具体形态未被分析。
